# お題生成パイプライン

## 全体の流れ

```
1. LLMに20件リクエスト（N_request = 20）
2. ホワイトリスト検査（正規表現。読み取得の前に無料で弾く）
3. getReading() で読み仮名・ローマ字を取得
4. 打鍵数10〜35の検査
5. 「含む」モードなら、指定文字が読み仮名に含まれるか検査
6. 有効数が目標に達していなければ、もう1ラウンドだけ繰り返す
7. D1へ保存（sequence_numberを現在の最大値+1から連番で採番）
```

## バリデーション

### 使用文字のホワイトリスト

読み取得の前に、生の出力へ正規表現をかける。

- **許可**: ひらがな・カタカナ・漢字・`、` `。` `ー` `！` `？`
- **拒否**: 上記以外すべて

「日本語以外を弾く」では不十分。`「」` `（）` `〜` `・` `：` は日本語だが**キーボードで打てない**ため、明示的なホワイトリストで弾く必要がある。

### 打鍵数

短文は10〜35打鍵、**単語は4〜20打鍵**（2〜3語の組み合わせを通すため。下の「単語モード」）。読み取得後に、`packages/shared` のかな→ローマ字候補テーブルを使って計算する（タイピング判定と同じテーブルを再利用するため追加実装は不要）。

漢字かな混じりの文字数では判定しない。「薔薇」2文字＝4打 vs「機械工学」4文字＝14打と3倍以上ぶれるため。

**生成プロンプト側にも長さの指示がある**（ひらがなに直して8〜18文字程度）。上限を35打に引き締めた際に合わせて変えた。プロンプトは打鍵数そのものを数えられないため、かな文字数で近似する。旧指示の「8〜20文字」のままだと、平均約2打/かなで36〜40打の文が量産され、上限変更の効果が却下率の悪化で消える。

### 「含む」モード

指定された文字が**読み仮名**に含まれるかを判定する。表記に現れていなくてよい（「座禅」は表記に「ざ」が無いが読み「ざぜん」に含まれる）。

### 単語モード

**指示も検証も短文とは別に持つ**（`wordRules()`）。短文用の指示を流用すると、
「8〜18文字」「文を途中で終わらせない」が効いて、**語ではなく短い文が返る**。
システムプロンプトでも「短文」と言わない。

| 検査 | 短文 | 単語 |
|---|---|---|
| 文字種 | ひらがな・カタカナ・漢字・`、` `。` `ー` `！` `？` | **句読点を落とす**（`ー` と `々` は残す） |
| 表記 | 漢字を1つ以上含む | **ひらがなだけを弾く** |
| 打鍵数 | 10〜35 | 4〜20 |

#### 1語に絞らない（2〜3語の組み合わせまで許す）

**テーマから連想できる単語は100語ほどで頭打ちになる。** 実測では「福岡」の単語プールが
93語に育った時点で、返ってくる語のほとんどが既出になり、**1回の生成で増えるのが数語**まで
落ちた。1プレイで20語消費するので、遊ぶほど追いつかなくなる。

そこで**2〜3語の組み合わせ**（「明太子パスタ」「天神の夜景」「博多祇園山笠」）まで許す。
組み合わせは掛け算で増えるため、語彙の天井が一気に上がる。

**ただし文は許さない。** 述語（〜する・〜だ・〜がある）が付いた時点で短文モードの領分になる。

**「文かどうか」は機械的に判定しない。** 表記から見分ける手段が無く、助詞で判定しようと
すると**「はかた」の「は」「たこ焼き」の「た」**を助詞と誤認して普通の語を大量に落とす。
文にしないことは**プロンプトの指示だけで担保する**（`wordRules()`。よい例・だめな例を挟む）。
検証側で効かせるのは文字種と打鍵数の枠だけ。

打鍵数の上限を20に上げたのはこのため（1語だけの頃は12）。**短文の範囲（10〜35）と
重なるが、それでよい**。短文と単語の違いは長さではなく「文かどうか」で、そこは打鍵数では
判定できない。

**例はテーマを明示して挟む。** 無記名の具体例を置くと few-shot と同じで、そのままの語を
返してくることがある。別テーマ（「祭り」）の例だと分かる形にして、真似させたいのは
**形だけ**にする。

**組み合わせは「個数」で指示する。**「1語でもよいし、2〜3語の組み合わせでもよい」と
許すだけの書き方では、**実測で返ってきた14語すべてが1語だった**（「デモ」「成果」
「スピード」…）。最適化モードで先に学んだのと同じで、**効くのは数えられる形にしたときだけ**。
半数以上を組み合わせにするよう指示している。全部を組み合わせにしないのは、打鍵数が上限に
寄って単語モードが短文モードに近づくため。

**単語に「漢字を1つ以上」は使えない。**「ラーメン」「モツ鍋」のようなカタカナ語まで
落ちる。狙いは「画面に出る表記がひらがなだけの、読むまでもないお題」を弾くことなので、
単語ではひらがな限定の側から判定する。却下のラベルは短文と共用する（`kanji`）。
**ラベルを増やさない**（AI Gateway のメタデータ5件の枠に収まらなくなる）。

**重複除去に渡す既存お題は、単語では200件遡る**（短文は30件）。単語は言い換えの幅が
無く、テーマから素直に連想すると同じ語が何度でも返る（「福岡」なら「屋台」「明太子」）。
30件では、31件目より前に作った語がそのまま二度入る。D1の読み取りが増えるだけで、
AIには渡さない（`INCLUDE_EXISTING_PROMPTS` は false）。

**単語モードはテーマだけ。** 最適化練習（「含む」モード）には付けない。短い語に
指定の音を入れさせるのは短文よりさらに却下率が上がり、実測で最大の却下要因である
`constraint` がそのまま効く（「ぬ」は短文でも15問に届かなかった）。

### 長文モード

**1本で1プレイ**（`PLAY_SIZE_LONG = 1`）。指示も検証の範囲も短文とは別に持つ（`longRules()`）。

| 検査 | 短文 | 長文 |
|---|---|---|
| 文字種 | ひらがな・カタカナ・漢字・`、` `。` `ー` `！` `？` | 同じ |
| 表記 | 漢字を1つ以上含む | 同じ |
| 打鍵数 | 10〜35 | **250〜450**（読み仮名でおよそ150〜220文字） |
| 1ラウンドの依頼数 | 20 | **5**（`N_REQUEST_LONG`） |

- **1本を1段落で書かせ、本と本の間は空行**にする。切り出しは `parseGeneratedBlocks()`（空行区切り）。
  行で切る短文用の `parseGeneratedLines()` を使うと、モデルが1文ごとに改行したときに1本が数件に割れ、
  どれも打鍵数不足で落ちる。空行が無ければ出力全体を1本と見なす
- **モデルは1文ごとに改行し、そのとき「。」を落とす**（実測: 「〜イベントだ／参加者は〜」）。行を
  そのまま繋ぐと「〜イベントだ参加者は〜」という区切りの無い文章になるので、**行末に文の終わりが無ければ
  「。」を補う**（`closeSentence`。「、」で終わる行には足さない）。プロンプトでも「各文の終わりに必ず
  「。」」と念を押す。それでも文の終わり（。！？）が `LONG_SENTENCE_MIN`（2）に満たない一続きは
  `punct` として却下する（区切りの無い文章は読みながら打てない）
- 1ラウンド5本なのは、1本≒短文15問ぶんの出力で20本頼むと応答が長すぎるため。在庫目標3本なら
  5本×2ラウンドで十分埋まり、読み取得も `2 × 5 = 10 ≤ 50` に収まる。`max_tokens` は既定の4000で足りる
- 既存お題の文脈は10本まで遡る（`LONG_EXISTING_CONTEXT_SIZE`）。本文が長いので必要以上に読まない
- 書き出しの制限（先頭4文字・3本まで）は短文と同じ
- **長文もテーマだけ**（最適化練習には付けない。単語と同じ理由）
- AI Gateway のメタデータの `path` は `regenerate:long` / `refill:long`

## リトライの規則

**最大2ラウンド（初回＋リトライ1回）。各ラウンドとも常にフル20件（長文は5本）をリクエストする。**

| パス | 目標 | 未達時 |
|---|---|---|
| 新規テーマ作成（同期） | 有効15件（**短文のみ**） | `GENERATION_FAILED` を返しテーマ名の変更を促す。**テーマ行は作らない** |
| 同期再生成（短文） | 有効15件 | `GENERATION_FAILED`。**1件も保存しない** |
| 同期再生成（**単語・長文**） | 有効20件／1本 | **取れた分を保存する。** 1件も作れなかったときだけ失敗（`docs/04-api.md`） |
| バックグラウンド補充（非同期） | その形式の在庫 ≥ オフセット + 目標 | `'difficult'` を立てる。**単語・長文は「1件も作れなかった」ときだけ** |

**単語と長文で条件を分けているのは、目標と上限が近いため**（`acceptsPartialBatch()`）。
1回の生成で作れるのは単語で最大40件、長文で最大10本しかなく、重複や却下でここから減る。
短文と同じ扱いにすると、少し届かないだけで有効なお題とニューロンを捨て、普通に作れている
テーマにまで「生成困難」の印が付いて補充が止まる。

### 単語の1プレイを20問にしている理由

**読み仮名の取得が外部APIだから。** Yahoo APIは1語につき外部サブリクエストを1回使い、
上限は1実行あたり50回。生成は40件が上限なので、**1プレイ30問にすると採用率75%を
要求する**ことになり、実際には届かない。届かなければ1プレイ分が揃わず、利用者は
「単語のお題を作る」を2〜3回押すことになる（1回につき約13ニューロン）。

20問なら40件中20件（採用率50%）で埋まり、たいてい1回で始められる。

**`getReading()` を形態素解析ライブラリへ差し替えたら30問に戻す。** 外部サブリクエストを
使わなくなればこの上限が外れ、1回の生成で30問ぶんを作れるようになる。値は
`packages/shared/src/session.ts` の `PLAY_SIZE_WORD` 1か所。

### この2ラウンド制限は勝手に変えてはいけない

Yahoo APIの呼び出しは **Workers無料プランの外部サブリクエスト上限（1回の実行につき50回）** を消費する。

```
20件 × 2ラウンド = 40回  → 収まる
20件 × 3ラウンド = 60回  → 超過して静かに失敗する
```

**`2 × N_request ≤ 50` を満たすこと。** N_requestを25に上げると2ラウンドで上限ちょうどになり余裕が消える。N_requestを変更する場合はラウンド数もセットで見直すこと。依頼数は形式ごと（`requestCount()`。長文は5本）で、どの形式でもこの式を満たす。

なお、Workers AIとD1への通信はCloudflare内部扱いで別枠（1000回）のため、この計算には含めない。

## バッチ間の重複対策

呼び出しはステートレスなので、2回目のバッチは1回目が何を作ったか知らない。対策は**2段**ある。

| 段 | 場所 | 効く範囲 | 状態 |
|---|---|---|---|
| 完全一致の除去 | `batch.ts` の `seen`（`new Set(input.existing)`） | 既存お題と**同一の文** | **有効** |
| プロンプトへの文脈 | `prompt.ts` の `INCLUDE_EXISTING_PROMPTS` | 言い回しの近い**別の文** | **いまは外している（試行中）** |

`seen` は読み取得の前に無料で弾く（既存お題の本文は `EXISTING_CONTEXT_SIZE` = 直近30件、**単語は200件**を取ってくる）。この段が生きている限り、**同じ文が二度プールに入ることはない。**

**弾いた数は `dup` として計測する。** 以前はカウンタを通さずに捨てていたため、**AI Gateway 上は「ほとんど却下されていない健全な生成」に見えるのに、実際の採用はごくわずか**という食い違いが起きた（福岡の単語プールで実際に起きた）。重複は却下の中で最も増えやすい要因なので、内訳に出しておく。

### プロンプトへの文脈を外して試している（2026-09-06〜）

直近30件を「これと似た内容・似た言い回しは避けろ」という否定の文脈として渡していたが、**モデルが内容ではなく形式の方に引きずられている疑いがある。** few-shot と同じで、否定で添えても例示は例示として効くため、お題の型（文の長さ・構文・主語の立て方）が既存に揃っていく。

**「慣れが生じない」ことがこのサービスの目的なので、型が揃うのは重複そのものより悪い。** 同じ文が出ないことは `seen` が保証しているため、外して失うのは「言い回しの近い別の文」の抑制だけ。

戻すときは `INCLUDE_EXISTING_PROMPTS` を `true` にする。載せる場合の入力トークンの増加は1バッチあたり約4ニューロン（0.005円程度）で、コストは判断材料にならない。**判断は却下率・重複率の実測（Phase 8）で行う。**

## 生成物の検証（お題の質）

打鍵できるかどうか（文字種・打鍵数・指定文字）とは別に、**お題としての質**をここで担保する。

| 検査 | 却下コード | 段階 | 理由 |
|---|---|---|---|
| 漢字を1つ以上含む | `kanji` | 読み取得の前（無料） | ひらがなだけの文は打てるが、画面に出るのは表記の方で、漢字かな混じり文を読みながら打つ練習から外れる |
| 同じ書き出しが上限まで無い | `opening` | 同上 | 1回の生成が1つの型で埋まるのを止める |

### 同じ書き出しの制限

先頭4文字が同じお題は、**1回の生成につき3本まで**（`OPENING_PREFIX_LENGTH` / `OPENING_MAX`）。

**プロンプトが効かなかったときの歯止め。** 「し」を指定すると、モデルは「しんしんと」を見つけて21件中14件をそれで埋めてきた（実測）。完全一致ではないので `seen` は素通りし、そのままプールに入ると「毎回違うお題」という前提が崩れる。

- 4文字なのは、「しんしんと」を削りつつ「しんぶん」「しんこう」「しんぱい」を別物として残せる粒度だから
- **既存お題は数えない。** 止めたいのは1回の生成の中の偏りで、過去のプールに何本あるかは別の話。既存を数えると、偏った状態で作られたプール（実測で同じ書き出しが23本）に塞がれて補充が失敗する
- ラウンドはまたいで数える（2ラウンド目で同じ型を作り直させない）

### 「含む」モードの偏り（2026-09-06の実測）

指示を足すたびに**別の抜け道に逃げる**ので、1つずつ塞いだ経過を残す。

| 指示 | 結果 |
|---|---|
| 「語頭に来る文は○個まで」 | **効かない。** 全体を数えさせる指示は守られない（文頭21/21） |
| 「どの文も指定文字を含まない語から書き始める」 | 文頭0%になるが、**文末の接続助詞に逃げた**（「〜したし」「面白し」。日本語として壊れる） |
| ＋「助詞や語尾として付け足さない」 | 日本語は自然になるが、**文頭に戻る**（「し」では100%） |

**位置の偏りは文字によって難易度が違う。** 「し」「ぴ」は語彙のほとんどが語頭に来るため、文中に置くこと自体が無理筋になる。「ざ」では文頭74%→56%まで下がった。

**擬音語・擬態語は勧めない側に倒さない。** 一度「使うと入れやすい」と書いたら「しんしんと」を量産したが、量産は `opening` の検査で止まるようになったため、語彙を狭める必要がなくなった。「ぴ」のように擬音語が語彙の中心にある文字では、禁じると生成そのものが失敗する。

### 却下率の実測（2026-09-06、qwen3 + `/no_think`）

| 文字 | 有効 | charset | kanji | opening | keystroke | constraint |
|---|---|---|---|---|---|---|
| ぴ（新規作成） | 17 | 0 | 11 | 少 | 0 | 0 |
| ぬ（新規作成・失敗） | 11 | 0 | 0 | 2 | 0 | **27** |
| ざ（補充） | 18 | 0 | 少 | 少 | 0 | 12 |

**`constraint` が最大の却下要因**。モデルが指定文字を読みに入れられないケースで、プロンプトでも検証でも減らせない。「ぬ」はこれで15問に届かず、新規作成が失敗する。プリセットに置く文字は、実際に作れるかを確認してから決めること。

## 読み仮名の取得

**必ず `getReading()` の抽象化を経由する。Yahoo APIを直接呼ばない。**

```ts
getReading(text: string): Promise<{ kana: string; roman: string[][] }>
```

MVPの実装はYahoo! JLP ルビ振りAPI（POST限定・JSON-RPC 2.0・1日50,000回・1分300回）。

**この抽象化は必須。** Yahoo APIは個人での商用利用が不可のため、将来の差し替えが確定している。後から挟むのでは間に合わない。

**差し替え先は形態素解析ライブラリ（Worker内で完結するもの）を予定している。** 外部サブリクエストを使わなくなると、`2 × N_request ≤ 50` の制約が外れる。**そのときに見直すもの**: 1ラウンドの依頼数（`N_REQUEST`）、ラウンド数、そして**単語の1プレイを20問から30問へ戻すこと**（`PLAY_SIZE_WORD`。理由は上の「単語の1プレイを20問にしている理由」）。

読みはお題生成時に一度だけ計算してD1に保存する。プレイのたびに呼ぶのではない。

**返す読みは必ずひらがなに揃えること。** Yahoo APIは漢字を含まない語にふりがなを返さず、表記をそのまま返す。「スピード」のようなカタカナ語がそのまま読みに混ざるため、ローマ字候補テーブルに渡す前にカタカナ→ひらがな変換を通す（`katakanaToHiragana`）。差し替え先の実装でも同じ保証が要る。

テーブルに無いかなが読みに残っていた場合は `UnsupportedKanaError` を投げ、呼び出し側がそのお題を却下する。

## 生成の発火条件（バックグラウンド補充）

プレイ開始でオフセットを更新した後に判定する。

**判定も補充も、遊んでいる形式のプールに対して行う**（短文を遊んでも単語は補充しない）。

```
残り = その形式の在庫 − 更新後オフセット

残り ≥ 30  → 何もしない
残り < 30  → ログインユーザーかつ allowRefill フラグ（Next.jsが
             残ニューロンを判定した結果）が true なら補充をキック
             匿名ユーザーや残数0ならキックしない
```

- 目標は「件数」ではなく**在庫水準**（その形式の在庫 ≥ オフセット + 30）。**単語もこの30を増やさない**（`docs/03-data-model.md`）
- 残ニューロンの判定はNext.js側が行い、`allowRefill` フラグとしてHonoへ渡る（`docs/04-api.md` の「判定と記録の分担」）
- `theme:<theme_id>:<form>:lock` で多重起動を防ぐ。最初の1件だけがロックを取得し、他はスキップする。**キーは形式ごと**（単語の補充中に短文の補充を止めない）
- `ctx.waitUntil()` を使い、レスポンスは待たせない
- **AIを呼んだ分は、成否によらず加算する。** お題が1件も増えなくても、読み取得の例外で落ちても、ニューロンは消費されている（`docs/04-api.md`）

## モデルの切り替え

`glm-4.7-flash` と `llama-3.2-3b-instruct` の両方を実装し、環境変数かパラメータで切り替えられるようにする。Phase 8で品質・速度・コストを実測して確定する。

比較候補と実測値（テーマ「忍者」8件・2026-09-05）。**モデルIDは推測で書かず `wrangler ai models` で確認すること**（存在しないIDを渡すと実行時に `5007: No such model` で落ちる）。

| モデル | 時間 | 採用 | ニューロン | 備考 |
|---|---|---|---|---|
| `@cf/qwen/qwen3-30b-a3b-fp8` + `/no_think` | 0.9〜1.6秒 | 6〜7/8 | 3.7〜4.2 | **既定** |
| `@cf/zai-org/glm-4.7-flash` | 24〜132秒 | 8/8 | 96〜215 | 品質は最高だが同期生成には遅すぎる |
| `@cf/meta/llama-3.1-8b-instruct-fp8` | 2〜8秒 | 0〜8/8 | 4〜6 | 書式を崩すことがある |

**Qwen3系には `/no_think` を付ける。** 推論モデルの「思考」も課金対象の出力トークンで、生成は1トークンずつ進むため時間にも直結する。お題生成は探索を要する問題ではないので思考させても品質は上がらず、むしろ思考中の連想メモに引きずられて内容が劣化する（実測で「忍者」の連想に `電話` `電車` `会社` が混ざり、それが最終出力に現れた）。

モデル固有の指示は `MODELS` の設定として持ち、パイプラインの中で分岐させない。

### 消費ニューロンの計算

**応答にニューロン数は入っていない。** `env.AI.run` が返す `usage` はトークン数だけ（`prompt_tokens` / `completion_tokens`）で、`usage.neurons` は存在しない。**日次上限の判定に使う値なので、モデル別の単価を掛けて自分で出す**（`MODELS` の `neurons`、計算は `neuronsUsed()`）。

| モデル | 入力（/百万トークン） | 出力（/百万トークン） |
|---|---|---|
| `@cf/qwen/qwen3-30b-a3b-fp8` | 4,625 | 30,475 |
| `@cf/zai-org/glm-4.7-flash` | 5,500 | 36,400 |
| `@cf/meta/llama-3.1-8b-instruct-fp8` | 13,778 | 26,128 |

既定モデルでの実測は**1ラウンド（20件リクエスト）で約6.5ニューロン**（2026-09-08、ローカルで新規作成1回）。出典は [Workers AI Pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)。**料金が変わったら `MODELS` を直す。** Cloudflareはモデル別の単価表示に変えたが、課金の裏側は引き続きニューロン。

単価かトークン数のどちらかが取れなければ**0**として扱う。推定値で埋めると、消費していない分まで利用者の枠を削ることになる。

### 枠を使い切ったときのエラー

無料枠（アカウント全体で1日10,000ニューロン）を超えると、Workers AI は **3036**（429）を返す。**Freeプランには超過課金の経路が無く、請求は発生せずエラーになるだけ**で、枠は 00:00 UTC に戻る。似た429に **3040**（Out of Capacity）があり、こちらは数分で直りうる。

`classifyAiError()`（`generation/ai.ts`）でこの2つを判別し、`AI_QUOTA_EXCEEDED` / `AI_UNAVAILABLE` として返す（`docs/04-api.md`）。**`GENERATION_FAILED` に落とさない。** 「テーマ名を変えて」は、名前を変えても直らない原因に対する誤誘導になる。

**背景補充では何もしない。** 誰も待っていない処理なので伝える先が無く、ログに残すだけ。利用者は在庫が尽きた時点で「作り足す」を押し、そこで同期生成のエラーとして正しい理由を受け取る。**このとき `generation_status = 'difficult'` を立てないこと。** アカウント側の枠切れは「このテーマは生成しにくい」とは別物で、印を立てると枠が戻った後も補充が止まる。

記録は `batch.ts` の **`onNeurons` でラウンドごとに、AIの応答が返った直後**に行う（完了を待ってから次へ進む）。戻り値（`BatchResult.neurons`）を待ってまとめて書くと、読み仮名の取得で例外が飛ぶ経路と、**クライアント切断でinvocationごと打ち切られる経路**で「AIは消費したのに記録されない」状態になる。`BatchResult.neurons` は合計値で、応答に載せる `neuronsUsed` に使う。

**`max_tokens` を明示すること。** モデル側の既定は2000で、推論モデルは思考だけで使い切って本文が空のまま返る。

**応答の形はモデルによって違う。** Workers AI の従来形 `{ response }` と OpenAI互換形 `{ choices[0].message.content }` の両方があるため、テキストの取り出しは正規化して受ける。これはモデルごとの分岐ではないので「モデル名で分岐しない」方針とは矛盾しない。

呼び出しは**AI Gateway経由**にする。

```ts
await env.AI.run(model, input, {
  gateway: {
    id: "henge",
    skipCache: true,
    metadata: { themeId, kind, round, path },
  },
})
```

これでレイテンシ・コスト・回数がダッシュボードに記録され、比較用の計測コードを自前で書かずに済む。生成したお題には `prompts.model` にモデル名を残し、どのモデルが作ったお題か後から辿れるようにする。

**`skipCache: true` を必ず付ける。** AI Gatewayのキャッシュが効くと、同じテーマに同じお題が返る。「毎回違うお題」というHENGEの前提が壊れるため、ダッシュボード側の設定に依存させない。

ゲートウェイは Authenticated Gateway を有効にする。バインディング経由の呼び出しは事前認証済みのため、APIトークンは発行しなくてよい。

## 計測

**呼び出しには必ずカスタムメタデータを付ける。** AI Gatewayのログは「AIとのやりとり」しか知らないため、これが無いと「どのテーマの生成か」でログを絞り込めない。

メタデータは**1リクエストにつき5件まで**（超過分は黙って捨てられる）。**出題の形式のためにキーを増やせない**ので、`path` の値に畳んである（`regenerate:word` / `refill:word`）。短文の値は変えていないため、既存の絞り込みはそのまま使える。値は文字列・数値・真偽値のみで、オブジェクトは入らない。枠の割り当ては次のとおり。

| キー | 付けるタイミング | 値 |
|---|---|---|
| `themeId` | リクエスト時 | テーマID |
| `kind` | リクエスト時 | `theme` / `constraint` |
| `round` | リクエスト時 | `1` / `2` |
| `path` | リクエスト時 | `create` / `regenerate` / `refill`（**単語は `regenerate:word` / `refill:word`**） |
| `counts` | `patchLog()` | `"charset:3,kanji:1,opening:2,keystroke:4,constraint:1,twice:5"` |

### 検証結果をログに書き戻す

生成の成否は、AIが応答した時点では分からない。読み取得と検証を通した後に判明する。この時間差は `patchLog()` で埋める。

```ts
const res = await env.AI.run(model, input, { gateway: { /* 上記 */ } })
const logId = env.AI.aiGatewayLogId

// ... ホワイトリスト検査 → getReading() → 打鍵数検査 → 「含む」検査 ...

ctx.waitUntil(
  env.AI.gateway("henge").patchLog(logId, {
    score: Math.round((valid / N_request) * 100),
    // **枠は残り1件しかない。** 内訳は必ず1つの文字列に畳む（下記）
    metadata: { counts: `charset:${c},kanji:${j},opening:${o},keystroke:${k},constraint:${n}` },
  }),
)
```

**却下率はここで見る。D1に却下数を記録するテーブルを作らない。** Phase 8のモデル比較と同じダッシュボードに並ぶ。

却下されたお題はD1に保存されないため、`prompts` テーブルからは却下率を計算できない（分母が残らない）。一方でAI Gatewayのログには落選分を含む生の応答が残っているので、原因を追うときはログ本文を読む。

**内訳は1つのキー（`counts`）に畳んで入れる。** メタデータは1リクエストにつき5件までで、リクエスト時に4件使っているため**patchLog で使える枠は残り1件だけ**。ここでキーを分けると6件目が黙って捨てられ、却下の内訳か採用の計測のどちらかが消える。例外もログも出ないので、ダッシュボードを開くまで気付けない。**項目を増やすときはこの文字列に足す。**

| ラベル | 意味 |
|---|---|
| `charset` | 却下。ホワイトリスト検査。打てない記号などが混ざっていた |
| `kanji` | 却下。漢字が1つも無い（ひらがなだけの文） |
| `opening` | 却下。同じ書き出しの文が既に採用上限まである |
| `keystroke` | 却下。打鍵数が10〜35の範囲外 |
| `constraint` | 却下。「含む」モードで、指定文字が読み仮名に無かった |
| `punct` | 却下。**長文のみ。** 文の終わり（。！？）が足りず、区切りの無い文章だった |
| `dup` | 却下。既にプールにある（または同じ生成の中で重なった）ため落とした |
| `twice` | **却下ではなく採用側の計測。** 指定文字を2回以上含んだ採用お題の数（最適化モードのみ） |

同じ却下率でも原因が違えば打ち手が変わる（記号ならプロンプトの指示、打鍵数なら長さの指示、含む文字ならテーマ自体の難しさ）。合計ではなく内訳で残すこと。

`patchLog()` は同期生成の待ち時間を増やさないよう `ctx.waitUntil()` に逃がす。

**`patchLog()` が外部サブリクエストを消費するか、Phase 3で実測すること。** バインディング経由なので内部扱いのはずだが、ドキュメントに明記が無い。外部扱いだった場合、`2 × N_request ≤ 50` の余裕が削られる。
