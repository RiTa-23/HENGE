# UI仕様

## 世界観

忍者・古風。派手さより「静かで研ぎ澄まされた」印象を優先する。

## 配色

**4色以内で描く。それ以外の色を足さない。**

| 名前 | 用途 |
|---|---|
| 墨（sumi） | 地の色 |
| 朱（shu） | **今すぐ打つべきもの**だけに使う |
| 金（kin） | 進行中・完了・装飾 |
| 生成り（kinari） | 文字・巻物の紙 |

朱と金の役割分担が重要。朱を待ち時間などに使うと「朱＝行動の対象」という意味が薄まる。

唯一の例外がロゴとアプリアイコン（下の「ロゴとアプリアイコン」）。それ以外の場所で朱を装飾に使わない。

値は `apps/frontend/app/globals.css` の `@theme` にある（墨 `#15171d` / 朱 `#d24a25` / 金 `#c9a45f` / 生成り `#ece2cf`）。

**濃淡は色を足さずに不透明度で作る**（`bg-kinari/5` など）。

**混色は4色から作る。5色目を足さない。** 混ぜた色も `@theme` に置き、使う側はトークン名で呼ぶ。

| トークン | 作り方 | 用途 |
|---|---|---|
| `--color-makibishi` | 朱に墨を混ぜる | 撒菱、打ち間違えたキー（＝ミス） |
| `--color-daidai` | 朱に金を混ぜる | キーボードの「次に打つキー」 |

**キーボードのハイライトだけ朱から橙へ移した。** 朱のままだと、隣で光るミスの赤と見分けがつかず、**打つべきキーと打ち間違えたキーが同じ色に見える**。巻物側（苦無・かなの現在位置）の朱は変えない。朱は引き続き「今すぐ打つべきもの」の色で、キーボードではその役割を橙が担う。

## 書体

| 用途 | 書体 | 配信方法 |
|---|---|---|
| 見出し・お題本文 | Shippori Mincho | Google Fonts CDN |
| UI周り | Zen Kaku Gothic New | Google Fonts CDN |
| ローマ字列・キーボード | JetBrains Mono | `next/font`で自己ホスト |

**日本語2書体をCDN経由にする理由**: お題が動的生成のため使用漢字を事前確定できず、ビルド時にサブセットを固定する自己ホストでは対応できない。Google Fonts CDNはunicode-rangeで100〜200文字ずつに分割配信し、ページごとに実際の使用文字だけを取得するため動的コンテンツに対応できる。

## Tailwindでのトークン化

配色4色と書体3種を `@theme` で定義し、**それ以外の色・書体を使えないようにする**。

```css
@theme {
  --color-sumi: ...;
  --color-shu: ...;
  --color-kin: ...;
  --color-kinari: ...;
  --font-mincho: "Shippori Mincho", serif;
  --font-gothic: "Zen Kaku Gothic New", sans-serif;
  --font-mono: "JetBrains Mono", monospace;
}
```

`bg-blue-600` のような汎用色や生の16進数値を書かないこと。

プレイ画面の忍者モチーフ（巻物・苦無・撒菱）はユーティリティクラスで表現しづらいため、**その部分だけ素のCSSで書く**。

## ロゴとアプリアイコン

ロゴは**アイコン＋ワードマーク（`HENGE`）**の組み。ヘッダー（`Logo`）は横並び、トップのヒーロー（`HeroLogo`）は縦積みで、構成そのものは同じ。

アイコンは `apps/frontend/app/icon.png`。**App Router の規約により、このファイルがそのまま favicon になる。**別途faviconを置かない。四方手裏剣（金の刃）に朱の弧を重ねたもの。

**画像に焼かれている色は、`@theme` のトークン値そのものではない**（朱 `#b1351d` / 金 `#ddb860` で、
トークンの `#d24a25` / `#c9a45f` とはずれる）。生成した絵をそのまま使っているため。色の系統は
4色に収まっているが、**アイコンを「トークンと同じ色」として扱わないこと。**画面側の色を
アイコンから採らない（`@theme` から採る）。

### これは3つのルールの例外

アイコンは下の3つに正面から反する。**いずれも意図した例外なので、見つけても直さないこと。
逆に、この3つが通用するのはアイコンの中だけで、アプリの画面には広げない。**

**1. 「朱は今すぐ打つべきものだけに使う」の例外。** ロゴとアイコンはブランドの表明であって、操作の対象ではない。

**2. 「プレイ画面のモチーフを流用しない」の例外。** 手裏剣は生成待ちのスピナーとして意味が決まっている（下の表）。ただしアプリアイコンが出るのは**アプリの外**（ブラウザのタブ・OSのホーム画面・ブックマーク）で、「回るはずの手裏剣が止まっている」という誤読は起きない。**アプリの中で手裏剣を静止させて置くことは、引き続きしない。**

**3. 「金は面で使わず、細い線までに留める」の例外。** 刃が金の面になっている。金を面で使わないのは、画面の中で**主役（打つべき文章と次に打つキー）より目立たせないため**の制約で、アイコンにはその競争相手がいない。**画面の中では引き続き、金は線までに留める**（巻物のキャップの帯が上限）。

### ワードマークの下に朱の一筆を引かない

以前はワードマークの下に朱の一筆（筆で払ったような下線）を引いていた。アイコンが朱の弧を持つので、両方置くと**朱の一筆が縦に2本並ぶ**。一筆はアイコン側へ移ったと考える。

### 背景は透過させる。地の色を焼き込まない

**アイコンは背景が透過した PNG で持つ。** 墨を塗った不透明な画像にしない。地の色を焼き込むと、
`@theme` の墨を将来変えたときに**アイコンだけ古い色のまま四角く浮く**。透過なら追従する。

差し替えるときは、地を抜いたうえで**縁のアンチエイリアスに地の色を割り戻す**こと
（ストレートアルファ）。抜いただけだと、明るい地に置いたときに縁が黒く縁取られる。
faviconはブラウザによって明るいUIの上に置かれるので、ここは実際に問題になる。

### トップのロゴは動く

トップのヒーロー（`HeroMark`）だけ、**朱の弧が手裏剣の周りを回る**。手前（楕円の下半分）では
刃の前、奥（上半分）では刃の後ろを通り、奥ほど小さく薄くなる。

**動かすのは朱だけ。刃は止める。** 動きが2つあるとページに入った瞬間の視線がロゴに集まる。
第一印象で読ませたいのはキャッチコピーの方。**ヘッダーの `Logo` も動かさない**（常時見えるもの
を動かさない）。視差効果を減らす設定のときは、元の絵と同じ静止画を1枚描いて止まる。

**平らな画像を y 軸で回しても奥行きにはならない。** 真横を向いた瞬間に消えて、その後は裏返る。
輪を回すのではなく、**輪の上を筆が走る**形にしてある。

### アイコンを差し替えたら、派生した2枚も作り直す

動かすために、`app/icon.png` から2枚を切り出してある。**元を差し替えると、この2枚だけ古いまま
残る**（OG画像と同じ罠。docs/09-share.md）。

| ファイル | 中身 | 作り方 |
|---|---|---|
| `public/logo-star.png` | 金の刃だけ | 軸穴から放射状に「金が最後に見える半径」を測り、4つの頂点と谷から多角形として引き直す。弧に隠れて短く出る谷は、4つの中央値に揃える |
| `public/logo-brush.png` | 朱の弧を帯に開いたもの | 楕円の中心線に沿って開き、刃に隠れた区間は隣の筆跡を持ってきて埋め、**帯を横一直線に整える**（うねったままだと筆が楕円から離れながら回って不自然になる） |

### 正方形で持つ

512×512。**長辺に合わせて縮めて、余りは透明で埋める。**縦横比が1でないと、faviconとして
渡ったときに正方形へ引き伸ばされて歪む。ページ内は `object-contain` なので影響しないが、
faviconは縮尺を選べない。

### `app/` に icon を2枚置かない

App Router は `app/icon.png` だけでなく `app/icon2.png` のような**連番も拾って
`<link rel="icon">` を複数吐く**。別案のアイコンを比較したくて `app/` に並べると、
**どちらがfaviconになるかブラウザ任せ**になる。使わない方は `app/` の外に置く。

## 狭い画面のヘッダー

`sm`（640px）未満では、**横並びのナビをやめてメニューに畳む**（`MobileNav`）。

375px幅で使える幅は327pxしかないのに、横並びのナビは**419px**要る
（お題一覧62／最適化46／お題を作る77／Googleでログイン162＋余白72）。**項目を減らさずに
収める方法が他にない。** ロゴ側も、ベータ版バッジ（78px）を落として280px→190pxにする。
バッジは表示であって操作ではないので、幅が足りないときに最初に落とす。

**ナビ項目は `components/nav-links.ts` に1か所で持つ。** 広い画面の横並びとメニューの中の
2か所に出るので、書き写すと片方だけ増えたり消えたりする。

メニューはヘッダーの**下に重ねる**（押し下げない）。開いた瞬間に本文がずれると、直前まで
見ていた位置を見失う。`Esc` で閉じる。

### ワードマークは段階ではなく画面幅に比例させる

トップのヒーローの `HENGE` は `clamp()` で幅に追従させる。`sm` で段階的に切り替えると、
**その手前の幅が必ず溢れる**（320pxでは `text-7xl` のワードマークが351pxになり、
使える幅272pxを超えて横スクロールが出ていた）。

## 忍者モチーフ

**常時表示するのは1つだけ。他は「その瞬間だけ」現れる。** 機能を持つものだけを使い、装飾目的では入れない。

| モチーフ | 出現 | 機能 | 色 |
|---|---|---|---|
| 手裏剣 | 生成待ちのローディング | 回転する道具＝スピナー | 金 |
| 苦無 | 常時（ローマ字列の現在位置） | 次に打つ文字を指すキャレット | 朱 |
| 撒菱 | タイプミス時。その問題が終わるまで残る | ミスしたローマ字の**真上**に置く | 朱より暗く鈍い赤 |
| 赤いキー | タイプミスの直後だけ（0.45秒） | **押してしまったキー**をキーボードに出す | 撒菱と同じ赤 |

**撒菱の詳細**

- ローマ字**1文字ごと**に紐づける（かな単位ではない）。`shi`の`h`で詰まるのか`s`で詰まるのかを区別する
- 同じ文字で複数回ミスしても撒菱は1つ
- その問題が終わるまで残し、次の問題で消す
- 苦無は文字の下、撒菱は文字の上に置くので衝突しない
- 既知の副作用として、入力経路が変わると撒菱の下の文字がずれることがある（`shi`表示中に2打目をミス→その後`si`確定で表示が変わる）。「何打目でつまずいたか」は正しいままなので許容する
- **形はSVG（`Makibishi.tsx`）で持つ。** 上へ長い棘が1本、下へ開いた脚が2本、そのあいだから手前へ短い棘が1本。`clip-path` の多角形で描いていたときは棘が等間隔・等長になり、**撒菱ではなくきらめきの記号に見えていた**。棘ごとに長さと角度を変えるには多角形1つでは足りない
- **縁取りを入れない。** 手前の棘を地の色で縁取って脚から切り分けると、そこに**黒いVの線**が浮き、撒菱そのものより先に目に入る。棘のあいだは地が覗くので、縁取らなくても形は割れる

**押してしまったキーは、その場でキーボードに返す。** 撒菱が「どこでつまずいたか」を問題の終わりまで残すのに対し、こちらは**何を押したか**を直後だけ出す（0.45秒）。短すぎると見る前に消え、長すぎると次の打鍵のハイライトと重なって、いま押したのかさっき押したのか読めなくなる。**受理されなかった打鍵だけ**を出す（打鍵として解釈できないキーはミスに数えていないので光らせない）。**赤が消える前にそのキーが「次に打つキー」になったら、橙を優先する**（`し` の `h` を先に打ってから `s` を打つと、次は `h`）。ここで赤を優先すると、いま押すべきキーが赤いままになり、この画面で消したかった混同がそのまま起きる。結果画面の苦手キー（打つべきだった文字を数える）とは別物で、あちらは弱点の集計、こちらはその瞬間の返答。

**撒菱は採用で確定した。** Phase 6 で実機プレイして判断済み（条件付き採用だった項目）。ミスが並んだ状態でも煩くないことを確認している。

### 形式の紋と「打つ」札

短文・単語・長文の「打つ」ボタンは、**すべて朱**（今すぐ打つべきもの）で色では区別しない。
色で分けると朱の意味が薄まる。見分けは**紋**（`FormMark`。形式を渡すと合った紋を返す。
呼び出し側に `form === "word" ? …` を書かせない）で付ける。

| 形式 | 紋 | 意味 |
|---|---|---|
| 短文 | 原稿用紙のマスが横に3つ | 文＝文字が並ぶ |
| 単語 | マスが1つ、中に点 | 語＝1つのかたまり |
| 長文 | マスが横に3つ×縦に2段 | 文章＝行が重なる |

原稿用紙にしたのは長さの違いが一目で分かるため（1マス／3マス／6マス）。巻物の開閉で表すと、
一覧のカード（閉じた巻物がほどける）と意味がぶつかる。**紋は「打つ」札だけでなく、
プレイ画面の開始前と結果のバッジにも同じものを置く**。どの画面でも同じ印で形式を示す。

ボタンは**木札**の形（`FormButton`）。角を1つ落として紐穴を空けた札で、巻物に結わえた札を
引くとその形式で打ち始まる、という見立て。角の落としは `clip-path` で、枠線は clip で
切れるので内側の影で描く。一覧は小（1行）、詳細は大（問題数の副題つき。長文は「1本を通しで」）。
テーマは3枚。一覧のカードは札3枚ぶんの高さを紙に持たせる（`min-h-32`。紙は `overflow: hidden`
なので、足りないと上下の札が切れる）。最適化練習は形式が1つなので「打つ」1枚（紋は短文）。

### モードの紋（トップの選択カード）

トップの第一画面は**ロゴ → キャッチコピー → モードの選択**の順に並べる。ロゴ（`HeroLogo`）はトップで一番大きく出す。ただし HENGE はブランドの表明であって見出しではないため、**`h1` はキャッチコピー側に置く**。

トップの「テーマで打つ／最適化練習」の選択カードには、**モードごとの紋**（`components/ModeMark.tsx`）を置く。**プレイ画面のモチーフは流用しない。** 手裏剣＝スピナー、苦無＝キャレット、撒菱＝ミスという意味がすでに決まっており、別の場所で静かに置くと薄まる（「回るはずの手裏剣が止まっている」「ミスでもないのに撒菱がある」ように見える）。**アプリの外に出るアプリアイコンだけが例外**（上の「ロゴとアプリアイコン」）。紋は**識別のための新しい線画**で、次の対応にする。

| モード | 紋 | 意味 |
|---|---|---|
| テーマで打つ | 巻物と文章の線 | 題材の文章を通しで読んで打つ |
| 最適化練習 | 的（まと） | 指定した音を狙い、繰り返し打ち込む修行 |

選定の経緯。最適化練習は初案（鍵盤2つと運指の弧）が実機で**「何を表しているか分からない」**と却下され、次に三つ巴を試した。三つ巴は体裁が最も整っていたが、最終的には**的**を採用した（「1つの連接に狙いを絞る」仕様と直結し、同心円なので小さいサイズでも崩れない）。テーマの紋も初案では軸が細線すぎて巻物と読めず、**軸を丸い円柱（角丸の矩形）にし、軸より細いキャップを上下に飛び出させた**（プレイ画面の巻物と同じ構成要素）。

**三つ巴は将来の機能のために保管する。** 選定段階で「最も体裁が整う紋」という評価があり、次に紋が要る機能（例: 追加モードや達成系の機能）で再利用する予定。再現するには次の線画を使う。stroke 3・`currentColor`、頭（`r=3.5` の塗りつぶし円）から尻尾が円弧に沿って時計回りに流れ、それを120°ずつ回して3巴にする。

```svg
<g fill="none" stroke="currentColor" stroke-width="3" stroke-linecap="round" stroke-linejoin="round">
  <g>
    <circle cx="32" cy="13" r="3.5" fill="currentColor" stroke="none" />
    <path d="M32 13 A 19 19 0 0 1 50.7 35.3" />
  </g>
  <g transform="rotate(120 32 32)">
    <circle cx="32" cy="13" r="3.5" fill="currentColor" stroke="none" />
    <path d="M32 13 A 19 19 0 0 1 50.7 35.3" />
  </g>
  <g transform="rotate(240 32 32)">
    <circle cx="32" cy="13" r="3.5" fill="currentColor" stroke="none" />
    <path d="M32 13 A 19 19 0 0 1 50.7 35.3" />
  </g>
</g>
```

この`<g>`を`viewBox="0 0 64 64"`のsvgに載せれば三つ巴が再現できる。線画の由来（選定時の候補と却下理由）は PR #91 を参照。

線画は stroke＋`currentColor` で描き、色は置く場所（カード）が制御する。ホバーで border とともに紋も浮かせる。

## 巻物

練習エリアは**巻物**のモチーフ。**一覧のカードも同じ巻物**（`.scroll--card`。軸・キャップ・紙の面をそのまま小さくしたもの）。別の作りにすると「一覧の巻物」と「プレイの巻物」が別の物体に見える。キャップが軸の外に張り出すぶん、並べるときは上下にキャップ高さ以上の余白を取る。

**両端は同じ材質・同じ色・同じ太さにする。** 巻物は一枚の紙に2本の軸が付いた1つの物体なので、色や太さを変えると別々の物体に見える。

**太さで在庫を表さない。** 当初は右の巻き残りの太さを在庫（総生成数 − オフセット）に連動させる案だったが、やめた。太さが動くと「いま何かが起きた」と誤読させるうえ、残りが何問かは太さより数字の方が正確に読み取れる。軸は左右とも固定の太さにする。

**紙は暗く、軸は明るい。** 広げた紙は墨に生成りを混ぜた暗い面（生成りをそのまま敷かない）。軸の円柱は紙と**同じ高さ**で、金と墨を混ぜたくすんだ薄い緑（竹軸のような色。生成りで淡く上げる）。紙より暗いキャップが軸の上下から飛び出す（軸に重ねない）。キャップは**軸より細く**し、外側の縁にだけ金の帯を入れる。

**巻きを画面で最も目立つ要素にしない。** 主役は打つべき文章と次に打つキー。金はキャップの外縁の帯までに留め、面で使わない。

| 管理: テーマ | `/admin/themes` | 管理者のみ | noindex |
| 管理: テーマのお題 | `/admin/themes/[id]` | 管理者のみ | noindex |
| 管理: ユーザー | `/admin/users` | 管理者のみ | noindex |

- **途中でやめられる。** プレイ中の「やめる」ボタン（`Esc` でも同じ）で開始前へ戻る。**取得済みのお題は捨てる。** 持ち回して再開できるようにすると、一度お題を見たうえで同じ15問を打ち直せてしまう。**暗記による有利を作らないことがこのサービスの前提**なので、見たお題を再配布しない。オフセットは受け取った時点で消費が確定しているため（`docs/04-api.md`）やめた分の在庫は戻らないが、それは中断の代償として受け入れる
- **お題を出す前に「はじめ！」の合図を挟む。** Space →（必要なら生成待ち）→ 合図 → 1問目。押した瞬間にお題が出ると構える間が無い。**合図のあいだは時間を数えない**（計時は合図が消えて1問目を出す瞬間から）。ここを間違えると WPM が実際より低く出て、**スコアが静かに壊れる**。合図のあいだはお題も出さない（見えていれば待つあいだに読めてしまう）。視差効果を減らす設定では動かさずに出す
- **プレイ画面は開いた時点では始めない。** 「スペースで開始」の画面を挟む。`POST /api/sessions/start` を呼んだ時点でオフセットの消費が確定し、条件次第では背景補充（＝クォータ1消費）も走るため、画面を開いただけでそれが起きると身に覚えのない消費になる。同じ画面から一覧へ戻せるようにする
- **テーマを作った直後に自動で始めない。** 「プレイする」か「テーマ作成に戻る」を選ばせる。続けて別のお題を作りたいこともあり、勝手に始めるとその場でお題を1組消費する
- 結果画面はプレイ画面内の状態として持つ。**プレイごとの履歴は持たない。** 残るのはランキングに登録したベストだけで、それも本人が「ランキングに登録」を押したときだけ（下の「結果画面」）
- **プレイ画面からの離脱先はテーマ詳細にする。トップへ返さない**（結果画面・枯渇画面とも）。トップに戻すと遊んでいた文脈が消えて探し直しになる。詳細には短文／単語の選択と在庫数があるので、**同じテーマの別の形式へそのまま移れる**。一覧（`/themes`・`/practice`）への導線は別に残す
- **結果の「もう一度」は `R` でも押せる。** 開始が `Space`、中断が `Esc` で済むのに、再挑戦のためだけにマウスへ手を戻すと、続けて打ちたいときに手が止まる。修飾キーとの同時押しは拾わない（`Cmd+R` / `Ctrl+R` のリロードを奪わないため）。開始前のスペースと同じく**窓側の keydown で拾う**。結果画面には投稿・一覧・トップへのリンクが並ぶので、フォーカスをどこかに固定するとそれらへキーボードで到達できなくなる
- **一覧のカードは巻物**（`ThemeCard`。一覧・トップの「よく打たれているお題」・最適化練習の一覧とも）。**3列の格子**に並べる（`sm` で2列、それ未満は1列）。**最初は閉じている**（軸2本と、名前が読めるだけの狭い紙。テーマ名とプレイ回数だけ）。**カーソルを合わせる（またはフォーカスが入る）と紙が横にほどけて**、巻かれていた側に畳まれていた「短文」「単語」の札が現れる。**縦幅は変えない**（巻物は横に巻くもの。下に伸びると別の物になる）。ホバーの無い端末では最初から開いておく（閉じたままだと打てない）
- 押せる場所が2種類ある。**巻物そのもの**を押すと詳細へ、ほどけた中の**ボタン**を押すとプレイへ直行する。以前はカード全体がプレイへ直行していたが、テーマに打ち方が2つできた時点で「カードがどちらかを勝手に選ぶ」形になり、単語モードが辿れなくなった
- **開閉で格子のセルは動かさない。** 巻物の幅がセルの中で変わるだけ（閉：200px／開：セルいっぱい）。ホバーのたびに一覧が組み替わると、目当てのカードを見失う。ボタンは紙の左端から固定の位置に置き、紙が狭い間は `overflow: hidden` で右の軸の下に隠す
- **「生成困難」の印は、どの形式が困難かを紋で示す**（`DifficultBadge`。形式の紋を並べて「困難」）。印は形式ごとに立つので、文字だけの「生成困難」では短文と単語のどちらの話か分からない。一覧・詳細・管理画面で同じ部品を使う。閉じた紙に収めるため一覧では「困難」に詰め、正式な文言は `title` に持たせる
- 巻物に載せるのは**テーマ名とプレイ回数**だけ。**お題数は詳細でのみ出す**（一覧のAPIに集計を持たせない。`docs/04-api.md`）
- 最適化する音のカードはボタンが「打つ」1つ（形式が1つなので）
- テーマ詳細は検索エンジンからの着地ページ。行き止まりにせず「打つ」を主役に置く。**広げた巻物1本**（`DetailScroll`。プレイ画面と同じ大きさの `.scroll`）に名前・説明・在庫・ボタンを載せる。一覧の閉じた巻物を押した先なので、同じ物体で受けると一覧 → 詳細 → プレイが1本の巻物で繋がる。紋（`ThemeMark` / `PracticeMark`）は見出しの肩に小さく置く（どちらのモードかの識別で、それ以上の装飾にしない）。金は罫線と紋の線まで。狭い画面では軸を細くする（`.scroll--detail`）
- **詳細ページの巻物の下にランキング**（`RankingBoard`。`#ranking`）。短文と単語は別の表で、タブで切り替える（両方をサーバーで描いて渡し、切り替えだけクライアント）。最適化する音は短文だけなのでタブを出さない。列は順位・名前・スコア・打鍵/秒・正確率で、値は結果画面と同じ関数から出す。名前は `user.display_name` の**いまの値**（登録時の名前ではない）。記録が無ければ「最初の1人になれます」
- **`ninja.css` はレイヤーに入っていないので、Tailwind のユーティリティより常に強い。** `.scroll` の `--roller-width` を `[--roller-width:26px]` のような任意プロパティで上書きしようとしても効かない。巻物の寸法を変えたいときは `ninja.css` 側に修飾クラスを足す（`.scroll--card` / `.scroll--detail`）
- **`SiteHeader` を置くページは `force-dynamic` にする。** ヘッダーはベータ表示の判定で Cloudflare のバインディングを引くので、静的生成するとビルド中に Miniflare が起動し、Nextのビルドワーカーが同じローカルSQLiteを奪い合って**ビルドが落ちる**（当たり外れがあり、PRのCIは通ってmainのデプロイだけ落ちる形で出る。#140）。静的な文章のページでも例外にしない
- **マイページ（`/me`）は自分のことだけを見る場所。** URLにIDを持たず、他人のページは無い。ユーザー名の編集、本日のニューロン（`残り N / 500`。リセットは日本時間の朝9時と表記）、作ったお題（テーマと最適化する音を分けず新しい順。`ThemeCard` の格子）の3つ。未ログインならログインを促す（`LoginRequired`。お題の作成と同じ部品）。ヘッダーのログイン中の表示（`LoginButton`）から辿る。**`NAV_LINKS` には入れない**（あちらは未ログインにも見せる固定の並び）
- **ユーザー名（表示名）が未設定のログインユーザーには、入力のモーダル（`DisplayNameGate`）を出す。** `SiteHeader` に置いてあるので、ヘッダーのある画面ならどこでログインしても出る。**閉じるボタンは置かない**（名前は公開の場に出す前提で、「あとで」を許すと未設定のまま公開の場に立つ）。抜けたければログアウトする。列を足す前に登録した利用者も未設定なので、次に開いたときに同じ導線に乗る。フォーム（`DisplayNameForm`）はマイページの編集と共用。**`/me` でも出る。** そこで保存するとマイページ側の入力欄もセッションから同じ名前で描き直される（`MyDisplayName` はサーバーの値ではなくセッションを見る）
- 管理画面はヘッダー等からリンクせず、直接URLでのみアクセスする
- 管理: ユーザー（`/admin/users`）は閲覧のみ。**当日の消費ニューロンを上限とセットで出す**（`19.5 / 500`）。上限に張り付いている利用者を見つけるための画面なので、上限判定と同じ単位で並べる。回数も併記するが、それは1回あたりの重さ（消費 ÷ 回数）を読むための分母
- 管理: テーマのお題（`/admin/themes/[id]`）は、テーマ一覧の名前リンクから入る。お題の中身を確認し、編集・削除できる。**編集で送るのは本文だけ**で、読み仮名・打鍵数はサーバー側で取り直す。削除では連番を詰め直さない（`docs/04-api.md`）

## 2つのモード（テーマ／最適化）

**排他**。どちらか一方を選ぶ。組み合わせ可能にすると「テーマ × 最適化する音」ごとに別プールが要り、生成回数とYahoo APIの消費が組合せ的に増える。

画面は**対称に作り、共通のものは分けない**。DB上も同じテーブル（`themes.kind` で区別）で、APIも `kind` 1つで分岐している。

### 呼び名（UIとデータ層で違う）

**画面に出す呼び名と、データ層の呼び名を意図的に分けている。** 利用者に見せるのは「何のための機能か」（運指の最適化）で、`constraint`（含む文字）は「どう実現しているか」の名前だから。

| 場面 | 呼び名 |
|---|---|
| 画面（モード名） | **最適化練習**。ヘッダーなど幅の狭いところは **最適化** |
| 画面（指定する対象） | **最適化する音** |
| プレイ画面の枯渇時 | **この音**（テーマ側は「このテーマ」）。`kindLabel()` が返す |
| コード・DB・API | `kind: 'constraint'`。日本語では**含む文字**（`docs/03-data-model.md`・`docs/04-api.md`・要件定義） |

**`apps/frontend` は「最適化」の語彙で統一し、`apps/backend` / `packages/shared` / データ層のドキュメントは「含む文字」のままにする。** 境界はこの1行で言い切れる形にしておくこと。データ層まで改名すると `constraint` という識別子と、要件定義・DB設計の語彙の両方とずれる。

なお「読み仮名に『ざ』を**含む**文章」のように、**仕組みを説明する動詞としての「含む」は残す**。これは呼び名ではなく事実の説明で、言い換えると不正確になる。

| | テーマ | 最適化 |
|---|---|---|
| 一覧 | `/themes` | `/practice` |
| 詳細（着地ページ） | `/themes/[name]` | `/practice/[char]` |
| 作成 | `/themes/new` | `/practice` の下部（`#create`） |
| プレイ | `/play/[theme]` | `/play/[theme]?kind=constraint` |

- 一覧の切替は `ModeTabs`（両方の一覧とトップに置く）。プレイ画面と作成フォームは**1つを共有し、`kind` を渡して文言と入力制限だけを変える**
- **プレイのURLは `kind` を持たなければならない。** 一意制約が `(kind, normalized_name)` なので、テーマ「ざ」と含む文字「ざ」は共存できる。名前だけではプールが決まらず、`kind` を落とすと**静かに別のプールを開く**。組み立ては `lib/ui/kind.ts`（`playHref` / `listHref` / `parseThemeKind`）に閉じ込め、各所で `?kind=` を手書きしない
- **プレイ画面をモードで分けない。** 打鍵の体験も、叩くAPIも、オフセットの扱いも同一。違うのは離脱先の一覧（`/themes` か `/practice`）と、枯渇時の呼び名（「このテーマ」／「この文字」）だけ

### `/practice` の構成

1. **代表的な最適化**（プリセット）: 運営が用意した指定（`lib/practice/presets.ts`）。**標準運指で同じ指が連続する並び**を選ぶ（`ざ`=`za` 左小指、`き`=`ki` 右中指、`de`=`で` 左中指）。最適化は苦手克服ではなく、標準運指を崩して速度を上げる上級者向けの技術なので、文言を「苦手」「詰まる」に寄せない。**既に生成済みのものは「すぐ遊べる」としてプレイへ直行**し、未生成のものは作成フォームへ文字を渡す（`?char=…#create`）。生成済みかの照合は表示名ではなく**正規化キー**で行う（結合濁点などの揺れで「作成済みなのに未生成に見える」のを防ぐ）
2. **みんなが作った指定**: 生成済みの最適化する音。待たずに遊べるので優先して見せる
3. **自分で指定する**: 自由入力。**ひらがな1〜4文字**。ログイン必須＋生成待ちが発生する（テーマ作成と同じ扱い）

**プリセットを主役に置く。** 自由入力は指定が分散してプールが増え、生成上限の消費が大きい。プリセットに集めるとプールを共有でき、「他の人が作った分をそのまま遊べる」状態になりやすい。

**プリセットにひらがな以外を混ぜない。** 判定は読み仮名に対して行うため、カタカナ・長音符「ー」・漢字は何にも一致しない。弾かれるのはAPIの入口だが、**画面上は普通のボタンに見えて押した人だけがエラーに当たる**。`lib/practice/presets.test.ts` で機械的に検査している。

**自由入力はクライアント側でもひらがなを検査する。** サーバーも `VALIDATION_ERROR` で弾くが、送ってしまうと `GENERATION_RATE_LIMIT`（5回/60秒）を1つ消費し、打ち間違いの数回で `RATE_LIMITED` に落ちる。判定は `packages/shared` の `isHiraganaOnly` を共有していて、規則の二重定義ではない。

## ベータモード

`BETA_MODE`（Next.js Worker の環境変数。`apps/frontend/wrangler.jsonc` の `vars`）が `"true"` の間はベータ運用。**`"true"` 以外（または削除）にして再デプロイすれば公開版に戻る**。判定は `lib/beta/beta.ts` に集約し、画面・APIの両方から使う。

| 機能 | ベータ版利用者 | 運営アカウント |
|---|---|---|
| 既存プールのプレイ（テーマ） | できる | できる |
| お題の補充生成（`/api/prompts/regenerate`・バックグラウンド補充） | できる | できる |
| 最適化練習（`/practice` 系・`?kind=constraint` のプレイ） | **調整中** | できる |
| お題の新規生成（`/themes/new`・`POST /api/themes`） | **調整中** | できる |

- **ベータ版利用者＝運営アカウント以外**（未ログインを含む）。運営の判定は `/api/admin/*` と同じ `ADMIN_EMAILS`（`isAdminEmail`）。**運営アカウントは何も変えず全機能が使える**
- **ロゴの横に「ベータ版」を出す**（`Logo` の `beta` prop、判定は `betaBadgeVisible()`）。これは制限ではなく**サイトの状態の表明**なので、**運営にも見せる**。プレイ画面も含め、ロゴが出る場所すべてに出る。**ただし `sm` 未満では出さない**（狭い画面ではロゴだけで幅が足りない。下の「狭い画面のヘッダー」）。envだけを見るためセッション照合は走らない
- 調整中の機能は**共通の `AdjustingView`**（`components/Adjusting.tsx`）を出す。機能への入口（ヘッダー・タブ・トップのカード）は残し、着地した先で調整中であることを伝える
- 調整中の間、最適化練習のページ（`/practice`、`/practice/[char]`）は**検索エンジンに noindex を返す**。着地ページの体裁を保てないため
- 制限は画面だけでなく**API（`POST /api/themes`）でも弾く**（`docs/04-api.md`）。UIを隠すだけでは直接叩かれたときに通ってしまう

## 効果音

打鍵音（受理された打鍵）とミス音の2つ。**音源ファイルを持たず、Web Audio API で合成する。**読み込み待ちが無く（1打目から鳴る）、Workerに載せる資産も増えない。

**打鍵音は拍子木（木を打ち合わせる音）を目指す。** 単一の波形を鳴らすだけでは電子音に聞こえるので、木の音と同じ3層で組む。

| 層 | 役割 | 作り方 |
|---|---|---|
| あたり | 押した瞬間の輪郭 | 雑音の一瞬（10ms）を高い帯域で抜く |
| 鳴り | 木らしさ。音色はここで決まる | 雑音を**高いQの帯域**で細く残す |
| 胴 | 手応え（重み） | 低い三角波を短く鳴らす |

- **1打ごとに高さと音量を少しずらす**（±6% / ±12%）。まったく同じ音が並ぶと、打鍵ではなく機械の警告音に聞こえる
- **合計で60ms程度に収める。** 長く伸ばすと、速く打ったときに前の音が残って濁る
- ミス音は打鍵音より**低く、長く、やや大きく**する。同じ長さにすると、速く打っているときに外したことに気付けない

- **AudioContext はユーザー操作の中で起こす**（開始の `Space`）。操作を伴わずに作った AudioContext はブラウザに止められたままになり、1問目が無音になる
- **消せるようにする。** 切り替えは開始前とプレイ中の両方に置く（`SoundToggle`）。開始前にしか無いと打鍵中に消せず、プレイ中にしか無いと「鳴ると分かってから消す」しかできない
- 設定は localStorage に持つ（**匿名ユーザーのデータをサーバーに持たない**＝不変条件10）。読めなければ**鳴る側に倒す**
- 鳴らすかどうかの判断は画面が持ち、`lib/play/sound.ts` は音を作るだけにする。状態を両方に持つと、消したはずなのに鳴る／その逆が起きる

## 出題の形式（短文／単語／長文）

各テーマを**短文**・**単語**・**長文**の3つの形式で遊べる。`kind`（テーマ／最適化）とは
**直交する軸**で、モードの切り替えではなく「同じテーマの打ち方の選択」。

| | 短文 | 単語 | 長文 |
|---|---|---|---|
| 1プレイ | 15問 | **20問** | **1本** |
| URL | `/play/[theme]` | `/play/[theme]?form=word` | `/play/[theme]?form=long` |

- **短文にクエリを付けない。** これまでに共有されたURLがそのまま短文で開く
- **形式の選択はテーマ詳細に集約する。** 一覧のカードは触らない（選択肢を2倍に並べても選びやすくならない）
- **単語のお題が1件も無いテーマでも、ボタンは出す。** 押すと枯渇と同じ導線（ログイン → 作る）に入る。ボタンごと隠すと「このテーマには単語が無い」ことすら伝わらない
- **空のプールに「使い切りました」と言わない。** 一度も遊んでいないので嘘になる。1件も無いときだけ「まだありません」に差し替える
- プレイ画面は開始前とヘッダーに形式を出す。**同じテーマ名で中身が変わる**ので、名前だけだと単語のつもりで短文を始めてしまう
- 単語・長文は**テーマだけ**。最適化練習には付けない（`docs/05-generation.md`）

### 長文の配置

**長文だけプレイ画面の配置が変わる。** 短文・単語の配置（巻物1問＋下にキーボード）をそのまま
使うと、文章が巻物に収まらず崩れる。

- **キーボードを出さない。** そのぶん巻物を縦に大きくする（`LongScroll`。`.scroll--long`。狭い画面では詳細と同じく軸を細くする）
- 紙の大半は**本文（漢字かな混じり）**で埋める。左揃え・行間広め。**本文に色は付けない**（表記と読みの対応を持っていないため。短文と同じ）
- 下の方に**読み仮名の行**と**ローマ字の行**。どちらも1行のまま `overflow: hidden` の窓に入れ、**いま打っている位置が窓の3割の位置に来るように横へスライド**する（折り返すと現在位置を目で探すことになる）。苦無・撒菱は短文と同じ置き方（ローマ字1文字の真下／真上）。窓の中に上下の余白を取る（外に出すと切れる）
- 進捗ドットは出さない（1本なので意味を持たない）。代わりに**1本の中の打鍵の進み**を細い金の線と `N/総打鍵` で出す
- 開始前は「長文・1本」、結果・X投稿は「長文」と出す

## 進捗表示

タイマーではなく**問題数ドット**。数は1プレイの問題数に合わせる（短文15／単語20）。時間制限はミスを誘発するため設けない。

## 結果画面

## 結果のスコア

**e-typing と同じ算出方法に合わせる。** 他のタイピングサイトの数字と比べられる方が、利用者にとって意味のある指標になる。

```
WPM   = ミスを含む総打鍵数 ÷ 秒 × 60
正確率 = 正確に打てた数 ÷ 総打鍵数
スコア = WPM ×（正確率）^3   … 小数点以下は切り捨て
```

**WPMの分子にミスを含めるのが要点。** ミスを除いた数で速さを数えると、ミスの分が正確率の3乗と合わせて二重に引かれる。

正確率が3乗で効くので、速さより正確さの影響が大きい。速度は分あたりではなく**1秒あたりの打鍵数**で表示する（1問ごとの体感に近い粒度のため）。計算は `packages/shared/src/score.ts` にあり、そこでテストしている。**結果画面・X投稿・ランキングの登録で同じ関数を使う**（ランキングはサーバーで計算し直すため、shared に置く）。

## 結果の苦手キー

15問を通して**打ち損ねた文字**を多い順に6つまで出す。

**押した誤りのキーではなく、打つべきだった文字を数える。** 「何を打ち損ねるか」は運指の弱点そのもので次に直す対象になるが、「代わりに何を押したか」は隣接キーの取り違えでばらけるだけで手がかりにならない。

- 候補が複数あるかな（`し` の `si`/`shi`/`ci` など）では、**画面に出ていた最短候補**の文字を数える。苦無が指していた文字と一致させるため
- 同数のときはキーの順で並べる。実行のたびに並びが変わると前回と比べられない
- 集計は問題ごとに作り直される（`TypingProgress.missedKeys`）ので、15問の通算は `apps/frontend/lib/play/misses.ts` で畳む

**最適化練習と地続きの機能。** ここに出た文字は、そのまま最適化練習で指定する候補になる。
