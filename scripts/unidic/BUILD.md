# UniDic トリム辞書のビルド手順

`apps/reading` で使う辞書 `unidic.dic.zst` の再現手順。通常は `bun run dict:fetch`
で Release アセットを取ればよく、ここは語彙を変えて作り直すときだけ必要。

## 成果物

| Release | ファイル | 語彙数 | zst | Wasm メモリ（実測delta） | sha256 |
|---|---|---|---|---|---|
| `unidic-cwj-trim-v2` | `unidic-cwj-v3.dic.zst`（使用中） | 539,203 | 6.0MB | +76.2MB | `a6ba1c111b139c4032a4bf808e9a97250341360ca8aa66ee96261d8e771da007` |
| `unidic-cwj-trim-v1` | `unidic-cwj-v7800n-slim2.dic.zst`（旧） | 539,835 | 6.9MB | +84.1MB | `aae2f56b6f88a2a6a2671a072248220166b708a1a4a8d2ffbff610d6c0d06d9f` |

ロード時ピーク = wasm delta + zstバッファ + ~12MB オーバーヘッド。v3 は ~94MB。

v3 は v7800n-slim2 で熟語を割って読んでいた原因（compact bigram 接続表が MeCab の接続行列より
全ペアで約5376低い・同形の動詞の行が重複除去で消えていた・頻出語が閾値で落ちていた）を直した辞書で、
お題860件の実測で正解率 73% → 88%、UNKNOWN_READING 23件 → 0件。調査は辞書リポジトリの
`reports/2026-10-reading-audit.md`。

## ビルド

**手順は辞書リポジトリ（RiTa-23/unidic-cwj-trim）の `scripts/build_dict.sh` に一本化した。**
cwj-3.1.1 の配布物の取得と sha256 照合 → `measure/` の vibtest で bigram 接続表を生成 →
`scripts/filter_lex_v3.py`（語彙の選定・語コスト +5376・特徴列の最小化）→ コンパイル → `zstd -19`。
同じ手順を辞書リポジトリの `build-dict` ワークフローが CI で回し、Release に上げる。
作り直すときは新しいタグに出し、このリポジトリの `fetch-dict.ts` のタグと sha256 を変える
（同じタグの辞書を差し替えると sha256 の照合で取得が止まる）。

- 接続は **compact connector（bigram方式）**。dense行列は cwj の ID 空間では辞書が膨らみすぎる
- 読み列は **f[24]（出現形正書法仮名）**。f[10] は語彙素読み（基本形、食べ→タベル）、
  f[13] は発音形（は→ワ、学生→ガクセー）なのでどちらも不適切
- 特徴列は `,,,,,,,読み,` に縮めてある（読み Worker は index 7 しか見ない）。wasm メモリが約8MB減る
- 圧縮に `--long=27` は付けないこと（ruzstd が128MBウィンドウバッファを wasm ヒープに確保し、
  実メモリが ~130-170MB 水増しされる）

## 計測方法

wasm delta = `initSync` 後の `memory.buffer.byteLength` の増分（bun で計測可能）。
本番推定は delta + ~12MB。正確には workerd の実 isolate で測ること（issue #183）。

## ユーザー辞書（誤読の個別修正）

システム辞書とは別に `apps/reading/assets/user-lex.csv`（MeCab 書式、
`表層,lid,rid,cost,特徴13列`）を Vibrato の
`reset_user_lexicon_from_reader` で重ねている。
**管理元は辞書リポジトリ（RiTa-23/unidic-cwj-trim）に移った**
（lid/rid が辞書ビルドの接続ID空間を参照するため、辞書と同じ場所で
バージョン管理する）。本リポジトリ側は `dict:fetch` で Release 資産を
取得するだけで、誤読の追加は辞書リポジトリへの PR になる。
誤読を見つけたら辞書リポジトリの CSV に1行足して PR を出す。マージ後の
Release の差し替え・HENGE の再デプロイ・既存お題の再読みは自動で続く（下の「反映の順序」）。

書き方:
- `lid`/`rid` はシステム辞書の接続ID空間の有効値が要る。
  **同じ品詞・同じ活用形の既存エントリから流用する**（lex_3_1.csv や
  トリム済みCSVを `^表層,` で引くと見つかる）
- **コストの基準（辞書 v3）**: 辞書 v3 は語コストに +5376 を足してあるので、csv の値は
  **ずらす前の基準 +5376** で書く。以下の数値はずらす前の基準で、csv には -20000 → -14624、
  3000 → 8376、7500 → 12876 のように書く。管理画面の承認値（-20000／3000）はずらす前の基準のままで、
  辞書リポジトリの apply-reports が csv に書くときに足す
- `cost`: 複合語・熟語（かき氷・屋台など）や明確に誤った語幹は
  **-20000**（強制勝ち）でよい。ただし **-20000 は既存の複合語を分解する**
  （例: `港` に付けると空港→そらみなと化）。単漢字・単一かな・
  名詞と同表層の動詞語幹など「同じ表層の別読みには勝ちたいが
  複合語は壊したくない」語は **3000 程度**に留める。
  迷ったら両方試して複合語が壊れない方を選ぶ
- **同じ表層の別読みを差し替えたいだけの場合**（例: `な` がナと読まれる
  べき所でナンに化ける）は、**誤読側エントリの lid/rid をそのまま借りて
  コストをその語の少し下にする**（`な,303,5296,7500,...,ナ` —
  ナンエントリは cost 7683）。コネクタ条件が同一になるので読みだけが
  入れ替わり、分解パスを余計に安くしない。単に安いコストの別エントリを
  足すと（-20000など）綺麗なは直るが 大きな→だいきな・
  行きなさい→いくきなさい のような分割回帰を誘発する
- **文脈で読みが変わる語は「表層+助詞」の複合エントリで文脈を束縛する**
  （例: `中` がナカと読まれるべき所でチュウに化ける →
  `の中で,7185,11365,-20000,...,ノナカデ`）。
  助詞を含めたエントリは `中` の後に助詞が来る位置にしかマッチしないので
  `彼の中国` や `試合中` のような「中で始まる複合語」を分解しない。
  エントリの **lid は先頭文字の語の lid、rid は末尾文字の語の rid** を
  借りる（の中X なら lid=の(7185)、rid=助詞の rid）と、エントリ前後の
  コネクタが本来の語境界と同じになり、次トークンの分解（広がる→こうがる
  等）を防げる。単に `の中` だけのエントリは `彼の中国→かれのなかこく` の
  ように複合語の先頭で誤ってマッチするので使えない
- **同じ表層に複数の正しい読みがある語**（例: `入っ` が文脈でハイッ/イッ
  に分かれる）を片方に寄せると、もう片方の文脈で誤読になる。
  強制勝ちさせたい読み（ハイッ）を -20000 で1行登録し、**壊れる側の
  複合語は語幹まるごとのエントリで保護する**（`気に入っ,...,キニイッ`、
  `立ち入っ,...,タチイッ` のように「語幹+入っ/入る」を -20000 で個別登録。
  同じ読みを出すだけの保護なので副作用はない）。
  両読みを同コストで登録する方式は、コネクタ近似誤差で間違った側を
  選ぶ文脈が残るため確実ではない
- 特徴列は読み（列12=index11）が必須、あとは pos1 の1文字＋`*` 埋めでよい
- **行追加の検証は辞書リポジトリの PR で完結させる。** 構文（13列・整数・
  カタカナ読み）に加え、誤読回帰（直したい読みになるか・複合語を壊さないか）と
  辞書語彙への巻き込み（その字を含む熟語の読みが変わらないか）を、マージ前に
  辞書リポジトリの CI が見る。**Release の差し替えはマージの後**なので、検査を
  通っていない行は HENGE に届かない。
  HENGE 側の `apps/reading` のテスト（`dictionary.test.ts`）は、取得した
  ユーザー辞書を**読み込めるか**だけを見る（読めないと読み Worker が起動のたびに
  落ちる）。中身の検査を HENGE に置くと、辞書の更新のたびに HENGE の無関係な
  PR の CI が落ちる
- **反映の順序**: 辞書リポジトリで user-lex.csv がマージされる → Release を
  差し替える → HENGE の Deploy を `reread: true` で起動する → Deploy が CI と
  デプロイを通したあとに、既存お題の再読み（`reread-prompts.yml`）を呼ぶ。
  再読みは生成時と同じ基準（打鍵数の範囲・最適化の字）で新しい読みを検査し、
  外れたお題は書き換えない（`skipped.tsv` に残る）
- **再読みは Deploy のたびに呼ばれ、取得した user-lex.csv のハッシュで走るかを決める。**
  その csv で再読みを終えていれば（Actions のキャッシュにキーがあれば）何もしない。
  `reread: true` の Deploy が、待機中に次の push の Deploy に置き換えられても
  （同じ concurrency グループで待機できるのは1本だけ）、次の Deploy が拾い直す

辞書本体の語彙を増やす根治はこちらの手順で `.dic` を作り直すが、
個別の誤読はユーザー辞書の方が軽い（再ビルド・再配布が不要）。
