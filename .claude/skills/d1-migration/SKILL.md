# D1マイグレーション

## 前提の確認

`docs/03-data-model.md` を読み、変更しようとしているテーブルの意図と制約を把握する。特に次の点に注意する。

- `themes` の一意制約は `(kind, normalized_name)`。`kind` を含めるのは、テーマ名「ざ」と含む文字「ざ」を共存させるため
- `prompts` の `(theme_id, sequence_number)` は、ページネーションと総生成数取得の両方を賄う
- 外部キーは `ON DELETE CASCADE` を明示する

## 手順

### 1. スキーマを編集する

`packages/shared`（または `apps/backend`）のDrizzleスキーマ定義を編集する。

**外部キーは `references()` を明示すること。** 書かないとFK自体が作られず、CASCADE削除が効かない。

```ts
themeId: text('theme_id')
  .notNull()
  .references(() => themes.id, { onDelete: 'cascade' })
```

### 2. マイグレーションを生成する

```bash
bun run db:generate
```

生成されたSQLを**必ず目で確認する**。Drizzleは意図しないテーブル再作成を生成することがある（SQLiteはALTER TABLEの機能が限られているため、カラム追加以外では新テーブルを作ってデータをコピーする形になりやすい）。データ量が増えてからこれが走ると危険。

### 3. ローカルで適用して検証する

```bash
bun run db:migrate:local
```

確認すること:

- 意図したテーブル・カラム・インデックスができているか
- **CASCADE削除が実際に効くか**（テーマを1件削除し、`prompts` と `user_theme_progress` が消えることを確認する）
- 既存データが壊れていないか

### 4. 本番への適用は自動で走る（PRをマージするだけ）

`main` へマージすると `deploy.yml` の `migrate` ジョブが適用する。**デプロイの前**に走り、失敗すればデプロイは止まる。**手で流す必要はない。**

D1のマイグレーションはサイレントに失敗する報告があるため、ジョブは `apply` の終了コードを信用せず、**適用後に `list` を実行し直して未適用が残っていないか確かめる**。残っていればそこで落ちる。

落ちたときは、GitHub Actions のサマリに「適用前の未適用 / 適用の出力 / 適用後の未適用」が残っているのでそこから読む。手で流し直すときは、手動トリガーの `D1 migrate` ワークフロー（`apply`）を使う。

**D1のマイグレーションは前進のみ。** 適用したものを戻す手段は無いので、間違えたときは**打ち消すマイグレーションを新しく足す**。だからこそ手順3のローカル検証を飛ばさないこと。

### 5. ドキュメントを更新する

`docs/03-data-model.md` のテーブル定義とインデックス一覧を更新する。カラムを追加した場合は、**なぜ必要なのかを一言添える**（後から見て消してよいか判断できるようにするため）。

## 注意点

- **KVのキャッシュはマイグレーションでは消えない。** テーマ関連のスキーマを変えた場合、KVに古い形式のデータが残っていないか確認する
- MVPのスコープ外（課金・対戦・お気に入り）のためのカラムを先回りで追加しない
