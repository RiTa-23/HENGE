# 不変条件レビュー

安いモデルが書いたコードは、**動くが不変条件を静かに破っている**ことが最大のリスク。「レビューして」だけでは表面的な承認に流れやすいため、この手順で機械的にチェックする。

## 前提の確認

レビュー対象のdiffを取得する（完成形だけでなく、**変更差分そのもの**を見ること。意図しない変更・スコープ外の追加はdiffでしか気付けない）。

```bash
git diff main...HEAD
```

## 手順

### 1. `AGENTS.md`（= `CLAUDE.md`）の不変条件11個を1つずつ照合する

読み飛ばさず、**該当するかしないかを11個すべてについて明示的に判定する**。「関係なさそう」も判定の1つ。

1. 認証はNext.js Workerのみか。Hono側にBetter Authを実装していないか。Honoに公開ルート（外部から直接届くルート）を生やしていないか
2. Service BindingsはHTTP方式（`env.BACKEND.fetch`）のままか。`WorkerEntrypoint`のRPC方式に変えていないか
3. 日次消費の日付は`packages/shared`の`usageDateKey()`（**00:00 UTC 基準**）を経由しているか。`new Date().toISOString()`の切り出しなどで日付を自前で作っていないか。**JSTに直していないか**（+9時間する・`Asia/Tokyo`で日付を切る等は違反。1人が上限の2倍まで消費できてしまう）。日本時間を使ってよいのは利用者への表示だけで、それも`quotaResetAt()`（朝9時として返す）を使っているか
4. 生成は最大2ラウンド（`MAX_ROUNDS`）のままか。1ラウンドの依頼数が単語40件・短文20件・長文5本のままか。各形式の1ラウンド依頼数が読み Worker の`MAX_TEXTS`（40）以下か。読み取得が1ラウンド1回のバッチ呼び出しにまとまっているか（1件ずつ・形式ごとに分けて呼んでいないか）
5. テーマ行はお題10問と同じバッチで挿入されているか（先に挿入していないか）
6. テーマ削除時にKVも明示的に消しているか（D1のCASCADEに任せていないか）
7. タイピング判定に`<input>` / `<textarea>`を使っていないか。`<div tabindex="0">`へのkeydownで実装しているか
8. 読み仮名の取得が`getReadings()`経由か。読み Worker を直接呼んでいないか
9. 色・書体がTailwindの`@theme`トークンのみか。生の16進値や`blue-600`のような汎用色クラスを使っていないか
10. 匿名ユーザーのデータをサーバー側に持っていないか（進捗はクライアントのlocalStorageか）
11. バックグラウンド補充の発火がログインユーザー限定か（匿名のプレイからキックしていないか）。発火した生成で使った**ニューロンをそのユーザーに加算**しているか（上限500ニューロン/日。**回数で数えていないか**）。**成果0件のときも、例外で落ちたときも加算しているか**（成功経路の最後でだけ記録していないか）

### 2. `MVPのスコープ外` リストに抵触していないか確認する

`AGENTS.md`の「MVPのスコープ外」（課金・対戦・ブラウザLLM・スコア履歴・OGP動的生成・Cron Triggers・Cache API・Workflows）に関するコード・カラム・インターフェースを**先回りで**書いていないか。「将来のために」という理由でのコード追加は却下する。

### 3. 該当する `docs/*.md` との整合性を確認する

変更内容に応じて読む。

| 変更対象 | 照合するdoc |
|---|---|
| DBスキーマ | `docs/03-data-model.md` |
| APIエンドポイント | `docs/04-api.md`（リクエスト/レスポンス形・エラーコード・Zod検証ルール） |
| 生成・リトライロジック | `docs/05-generation.md` |
| ローマ字入力・キーボード | `docs/06-typing-engine.md` |
| 画面・スタイル | `docs/07-ui.md` |

docsに書かれている仕様と実装が食い違う場合、**どちらが正しいかをその場で判断しない**。実装ミスかdocsの記述漏れかを切り分けて指摘する。

### 4. 指摘を構造化して返す

「良さそうです」を許さない形式で出す。問題がなければ空でよい。

- **file:line**
- 何が問題か（不変条件何番／docsのどの記述と食い違うか）
- どういう入力・操作で実際に壊れるか（具体的なシナリオ。「〜かもしれない」で終わらせない）

### 5. 指摘なしで通った場合も、確認した項目を明示する

「不変条件1〜11、スコープ外リスト、`docs/04-api.md`と照合し、問題なし」のように、**何を確認したか**を書く。「大丈夫そうです」だけだと、本当に11個照合したのか、見た目で判断したのか区別がつかない。

## やってはいけないこと

- diffを見ずに完成形のファイルだけで判断する
- 不変条件を「だいたい守られてそう」とまとめて済ませる（1つずつ判定する）
- 指摘を伴わない「良い実装だと思います」で終える
- レビュー対象のコードを自分で直接書き換える（指摘に留め、修正は書いた側に戻す。指摘と修正を同一パスで混ぜると、何を指摘したのか追えなくなる）
