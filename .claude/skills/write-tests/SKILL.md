# テストの書き方

「テストを書いて」とだけ指示すると、分岐のない表示コンポーネントにまでテストを書いて工数を無駄にしたり、逆に不変条件が絡む危ないロジックを飛ばしたりする。**何をテストするかの判断が、書き方そのものより重要。**

## 1. 書く／書かないを判定する

### 書く

- `packages/shared` の純粋関数（ローマ字変換、正規化、JST日付変換、クォータ計算など）。分岐が多く、バグが静かに紛れ込みやすい
- `CLAUDE.md` の不変条件が絡むロジック（判定順序、ログイン限定条件、CASCADE削除など）
- Zodの検証ルール（`kind`によって許可する入力が分岐するもの）
- リトライ・閾値判定（生成の2ラウンド制限、在庫30件での補充判定など）

### 書かない

- 見た目だけの表示コンポーネント（propsをそのまま表示するだけで、分岐がないもの）
- レイアウト・スタイリングのみのコンポーネント
- 外部ライブラリの薄いラッパー（自前のロジックを持たない呼び出しだけの部分）

### 境界のケース（UIとロジックが混ざる箇所）

タイピング入力のように、UIコンポーネントの内部に判定ロジックがあると「テストすべきかどうか」で迷う。この場合は**ロジックを`packages/shared`の純粋関数に切り出してそちらをテストし、DOMへの配線部分（keydownハンドラの薄い層自体）はテストせずブラウザで目視確認する**。UIコンポーネント自体を頑張ってテストしようとしない。迷ったら、判定ロジックを切り出せないか先に検討する。

## 2. テストケースの出所を確認する

思いつきでケースを作らない。既に仕様として書かれているものを先に拾う。

- `CLAUDE.md`の不変条件11個のうち、変更箇所に該当するもの。**正常系だけでなく、破ったら失敗するテストを書く**（例: 生成失敗時にクォータが加算されていないことを確認する。不変条件を守れているかは「正しく動く」だけでは検証できない）
- 該当する`docs/*.md`に明示的な「テストカバレッジ」の記述がある場合はそれに従う。特に`docs/06-typing-engine.md`（ん3パターン・拗音3系統・分解入力・外来語かな・最短候補での打鍵数計算など）は網羅すべきケースが列挙されている
- `docs/04-api.md`のエラーコード表・Zod検証表にある分岐は、正常系と異常系の両方をケース化する

## 3. ツールを使い分ける

| 対象 | 使うもの |
|---|---|
| D1/KVに依存しない純粋な変換・計算 | `bun test` |
| D1/KVに依存する処理 | Vitest + `@cloudflare/vitest-pool-workers` |

依存の有無で機械的に決まる。「念のためVitestで」のように重い方に寄せない。

## 4. 順序・条件分岐は明示的にテストする

不変条件には「順序」や「条件」が本質のものが多い。これらは実装が動いているだけでは壊れていることに気付けない。

- クォータは**生成成功後にのみ**加算される（先に加算 → 失敗時にクォータだけ減る、という壊れ方を再現できるケースを書く）
- バックグラウンド補充は**ログインユーザーの発火に限る**（匿名ユーザーのリクエストで補充がキックされないことを確認する）
- テーマ削除時はKVも消える（D1側だけ消えてKVが残る、という壊れ方を再現できるケースを書く）

## やってはいけないこと

- 分岐のない表示コンポーネントにテストを書く（ブラウザでの目視確認に任せる）
- テストケースを仕様を読まずに思いつきで作る（既存のdocs・不変条件から拾う）
- 「動く」ことだけを確認し、不変条件が破られたときに落ちるかを確認しない
