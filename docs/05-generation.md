# お題生成パイプライン

## 全体の流れ

```
1. LLMに形式ごとの件数をリクエスト（単語40・短文20・長文5）
2. ホワイトリスト検査・NG語検査（正規表現。読み取得の前に無料で弾く）
3. getReading() で読み仮名・ローマ字を取得
4. 打鍵数10〜35の検査
5. 「含む」モードなら、指定文字が読み仮名に含まれるか検査（指定の音を含む語は、こちらで選んで渡してある）
6. 有効数が目標に達していなければ、もう1ラウンドだけ繰り返す
7. D1へ保存（sequence_numberを現在の最大値+1から連番で採番）
```

## バリデーション

### 使用文字のホワイトリスト

読み取得の前に、生の出力へ正規表現をかける。

- **許可**: ひらがな・カタカナ・漢字・`、` `。` `ー` `！` `？`
- **拒否**: 上記以外すべて

「日本語以外を弾く」では不十分。`「」` `（）` `〜` `・` `：` は日本語だが**キーボードで打てない**ため、明示的なホワイトリストで弾く必要がある。

### 打鍵数

短文は10〜35打鍵、**単語は4〜20打鍵**（2〜3語の組み合わせを通すため。下の「単語モード」）。読み取得後に、`packages/shared` のかな→ローマ字候補テーブルを使って計算する（タイピング判定と同じテーブルを再利用するため追加実装は不要）。

漢字かな混じりの文字数では判定しない。「薔薇」2文字＝4打 vs「機械工学」4文字＝14打と3倍以上ぶれるため。

**生成プロンプト側にも長さの指示がある**（ひらがなに直して8〜18文字程度）。上限を35打に引き締めた際に合わせて変えた。プロンプトは打鍵数そのものを数えられないため、かな文字数で近似する。旧指示の「8〜20文字」のままだと、平均約2打/かなで36〜40打の文が量産され、上限変更の効果が却下率の悪化で消える。

### 「含む」モード

指定された文字が**読み仮名**に含まれるかを判定する。表記に現れていなくてよい（「座禅」は表記に「ざ」が無いが読み「ざぜん」に含まれる）。

**指定の音を含む語は、モデルに探させずにこちらで渡す**（下の「最適化練習の語彙」）。

### 単語モード

**指示も検証も短文とは別に持つ**（`wordRules()`）。短文用の指示を流用すると、
「8〜18文字」「文を途中で終わらせない」が効いて、**語ではなく短い文が返る**。
システムプロンプトでも「短文」と言わない。

| 検査 | 短文 | 単語 |
|---|---|---|
| 文字種 | ひらがな・カタカナ・漢字・`、` `。` `ー` `！` `？` | **句読点を落とす**（`ー` と `々` は残す） |
| 表記 | 漢字を1つ以上含む | **ひらがなだけを弾く** |
| 打鍵数 | 10〜35 | 4〜20 |

#### 1語に絞らない（2〜3語の組み合わせまで許す）

**テーマから連想できる単語は100語ほどで頭打ちになる。** 実測では「福岡」の単語プールが
93語に育った時点で、返ってくる語のほとんどが既出になり、**1回の生成で増えるのが数語**まで
落ちた。1プレイで20語消費するので、遊ぶほど追いつかなくなる。

そこで**2〜3語の組み合わせ**（「明太子パスタ」「天神の夜景」「博多祇園山笠」）まで許す。
組み合わせは掛け算で増えるため、語彙の天井が一気に上がる。

**ただし文は許さない。** 述語（〜する・〜だ・〜がある）が付いた時点で短文モードの領分になる。

**「文かどうか」は機械的に判定しない。** 表記から見分ける手段が無く、助詞で判定しようと
すると**「はかた」の「は」「たこ焼き」の「た」**を助詞と誤認して普通の語を大量に落とす。
文にしないことは**プロンプトの指示だけで担保する**（`wordRules()`。よい例・だめな例を挟む）。
検証側で効かせるのは文字種と打鍵数の枠だけ。

打鍵数の上限を20に上げたのはこのため（1語だけの頃は12）。**短文の範囲（10〜35）と
重なるが、それでよい**。短文と単語の違いは長さではなく「文かどうか」で、そこは打鍵数では
判定できない。

**例はテーマを明示して挟む。** 無記名の具体例を置くと few-shot と同じで、そのままの語を
返してくることがある。別テーマ（「祭り」）の例だと分かる形にして、真似させたいのは
**形だけ**にする。

**組み合わせは「個数」で指示する。**「1語でもよいし、2〜3語の組み合わせでもよい」と
許すだけの書き方では、**実測で返ってきた14語すべてが1語だった**（「デモ」「成果」
「スピード」…）。最適化モードで先に学んだのと同じで、**効くのは数えられる形にしたときだけ**。
半数以上を組み合わせにするよう指示している。全部を組み合わせにしないのは、打鍵数が上限に
寄って単語モードが短文モードに近づくため。

**単語に「漢字を1つ以上」は使えない。**「ラーメン」「モツ鍋」のようなカタカナ語まで
落ちる。狙いは「画面に出る表記がひらがなだけの、読むまでもないお題」を弾くことなので、
単語ではひらがな限定の側から判定する。却下のラベルは短文と共用する（`kanji`）。
**ラベルを増やさない**（AI Gateway のメタデータ5件の枠に収まらなくなる）。

**重複除去に渡す既存お題は、単語では200件遡る**（短文は30件）。単語は言い換えの幅が
無く、テーマから素直に連想すると同じ語が何度でも返る（「福岡」なら「屋台」「明太子」）。
30件では、31件目より前に作った語がそのまま二度入る。D1の読み取りが増えるだけで、
AIには渡さない（`INCLUDE_EXISTING_PROMPTS` は false）。

**単語モードはテーマだけ。** 最適化練習（「含む」モード）には付けない。短い語に
指定の音を入れさせるのは短文よりさらに却下率が上がり、実測で最大の却下要因である
`constraint` がそのまま効く（「ぬ」は短文でも10問に届かなかった）。

### 長文モード

**1本で1プレイ**（`PLAY_SIZE_LONG = 1`）。指示も検証の範囲も短文とは別に持つ（`longRules()`）。

| 検査 | 短文 | 長文 |
|---|---|---|
| 文字種 | ひらがな・カタカナ・漢字・`、` `。` `ー` `！` `？` | 同じ |
| 表記 | 漢字を1つ以上含む | 同じ |
| 打鍵数 | 10〜35 | **250〜450**（読み仮名でおよそ150〜220文字） |
| 1ラウンドの依頼数 | 20 | **5**（`N_REQUEST_LONG`） |

- **1本を1段落で書かせ、本と本の間は空行**にする。切り出しは `parseGeneratedBlocks()`（空行区切り）。
  行で切る短文用の `parseGeneratedLines()` を使うと、モデルが1文ごとに改行したときに1本が数件に割れ、
  どれも打鍵数不足で落ちる。空行が無ければ出力全体を1本と見なす
- **モデルは1文ごとに改行し、そのとき「。」を落とす**（実測: 「〜イベントだ／参加者は〜」）。行を
  そのまま繋ぐと「〜イベントだ参加者は〜」という区切りの無い文章になるので、**行末に文の終わりが無ければ
  「。」を補う**（`closeSentence`。「、」で終わる行には足さない）。**行＝文と見なす割り切り**なので、
  モデルが文の途中で折り返した行にも「。」が入り「〜アイデアを。形にする〜」のような文ができうる
  （実測では行＝文だった。変な位置の「。」を見たらここが原因）。プロンプトでも「各文の終わりに必ず
  「。」」と念を押す。それでも文の終わり（。！？）が `LONG_SENTENCE_MIN`（2）に満たない一続きは
  `punct` として却下する（区切りの無い文章は読みながら打てない）
- 1ラウンド5本なのは、1本≒短文1プレイぶんの出力で20本頼むと応答が長すぎるため。在庫目標3本なら
  5本×2ラウンドで十分埋まる。`max_tokens` は既定の4000で足りる
- 既存お題の文脈は10本まで遡る（`LONG_EXISTING_CONTEXT_SIZE`）。本文が長いので必要以上に読まない
- 書き出しの制限（先頭4文字・3本まで）は短文と同じ
- **長文もテーマだけ**（最適化練習には付けない。単語と同じ理由）。`POST /prompts/regenerate` は
  `kind: 'constraint'` に `sentence` 以外の形式が来たら `VALIDATION_ERROR` で弾く（URLを手で書けば
  プレイ画面まで辿り着けるので、作る口で塞ぐ。長文の指示は指定文字を入れさせないため、通すと
  偶然含んだ本だけのプールができる）
- AI Gateway のメタデータの `path` は `regenerate:long` / `refill:long`

## 最適化練習の語彙

**語は辞書から選んで渡し、モデルには「その語を使った自然な短文」を作らせるだけにする。**

モデルに「読みに『ざ』を含む短文を作れ」と頼む方式では、既定モデルが「読みに指定の音を含む漢字の語」をほとんど
思い浮かべられず、**文頭に指定の音を書いてから続きを作る**ことに逃げた。本番「ざ」の28件（2026-10-24）は
**すべて「ざ」始まり**で、7件はひらがなの作り語（「ざいりつを訪れた」「ざいしんを送った」）、「ざわめく」5件・
「ざい〜」8件のように**実質10語前後の使い回し**だった。位置・品詞・回数を個数で縛る指示（下の「『含む』モードの
偏り」）はほぼ効いていなかった。

| 段 | 中身 | 置き場所 |
|---|---|---|
| 共通語彙リスト | UniDic から選んだ普通の語の表記と読み。**全部の最適化で1本**（28,703語） | `apps/backend/src/generation/vocabulary.generated.ts`（`scripts/vocabulary/build.py` が作る） |
| 最適化ごとの語彙 | 共通リストから、読みに指定の連接を含む語をよく使われる順に最大1000語 | D1 の `constraint_vocabularies`（作成時に保存。`docs/03-data-model.md`） |

- **共通リストの選び方**は `scripts/vocabulary/README.md`。見出し（基本形）単位・固有名詞なし・zipf 2.0 以上・NG 語なし・
  1文字の語なし・語の断片なし・**その表記の最も普通の解析がその語であるものだけ**（頻度は表記単位で引くので、外さないと
  「ます」（升）に助動詞の頻度が付いて上位に来る）。読みの正解付きコーパスで、渡した語が狙いの読みで使われる割合は 0.99
  （「表記の持ち主に絞る」を入れる前の規則での実測）
- **規則で拾えない語は、1語ずつ目で判定して外す**（`scripts/vocabulary/excluded.tsv`、2,062語）。語の断片（「ザキ」
  「取り掛かり」）・意味の取りにくい語やごく狭い分野の専門語（「財経」「ハドロン」「リバタリアニズム」、知らない人が多い
  固有名詞「アルディージャ」）・お題に向かない語（医療・性の周辺、「座薬」「ボンデージ」）・読み違い（「鐘楼=しゅうろう」）。
  **俗語・ネット用語・固有名詞（商品名・チーム名・作品名）は外さない**（知られたものは文に混ぜて打てる）。暴力・死に
  関わる語と硬い語も残す
- **100語に届かない連接は作成を断る**（AI を呼ぶ前。`docs/04-api.md`）。拗音の大半・を・ぢ・づ・ゔ・でき・ぬの・ぺん が該当する。
  小書きのかなで始まる音（ゃ・ぃ など）は、それより前の入力検証で断る（下の「打鍵の単位で照合する」）
- 照合は検証と同じ `includesConstraint`。濁点・半濁点の違いは別の連接（「発表（はっぴょう）」は「ひょう」に当たらない）
- 保存済みの語彙も**読み出すたびに照合し直す**（`loadConstraintVocabulary`）。下の「打鍵の単位で照合する」を入れる前に
  保存した語彙には、字面だけ当たる語（「で」に「ディスク」）が入っているため。外した結果が100語に届かなければ AI を呼ばない

### 打鍵の単位で照合する

**「含む」は文字列の部分一致ではなく、打鍵の単位（`splitKanaUnits`）の並びで見る**（`findConstraintSpans`）。
字面では含まれていても、打つときには別のかなになるものがあるため。部分一致のままだと、練習したい連接を
1度も打たないお題が採用され、プレイ画面ではそこに的が立つ。

| 字面 | 打ち方 | 扱い |
|---|---|---|
| 「で」と「でぃすく」 | `dhi` で、`de` を打たない | **当てない**（後ろの小書きのかなと1単位になる。きゃ・しぇ・ふぁ・うぉ・つぁ・とぅ・ゔぁ も同じ） |
| 「ゃ」と「きゃく」 | `kya` の一部で、`xya` を単独では打たない | **当てない**（小書きで始まる音は、前と組まない箇所にしか当たらない。作成フォームとAPIの入口で断る） |
| 「きっ」と「きっ。」 | 次が母音・記号・文末だと「っ」は `ltu` | **当てない**（最後が「っ」の音は、次のかなの子音を借りる箇所だけ） |
| 「き」と「がっき」 | 「っ」は前に子音を足すだけで、「き」は `ki` のまま | 当てる |
| 「かん」と「かんい」 | 「ん」が `nn` になるが、`n` から打ち始める | 当てる |

- 単位の切り方は打鍵の候補と同じ表（`KANA_TABLE` の2かなの組）で決まる。組を足すと照合も自動で変わる
  （たとえば `てゃ` を足すと、「て」は「てゃ」に当たらなくなる）
- この切り方で、共通語彙リストの当たる語数は「き」3,200→2,332、「し」4,828→2,656、「で」542→397 に減る
  （2026-10-25）。プリセットの3つはどれも下限を大きく超えている

### 生成のたびに語を選ぶ

1. 生成の最初に、その最適化の語彙を**シャッフル**する
2. 1ラウンド目は先頭から、2ラウンド目は続きから、20文ぶんの語を取って組にする（**1回の生成の中で語が重ならない**）
3. 「次の各行に並べた語を使って、自然な短文を1つずつ作ってください」と頼む（`constraintRules()`）。
   語は活用させたり助詞を付けたりしてよいが、別の語に言い換えさせない
4. 検証は今までどおり（読みに指定の連接が入っているか）

- **指定の音そのものはプロンプトに書かない。** 書くと、渡した語を無視してその音で書き始める癖が戻る
- **語ごとの使用回数も、次に使う位置も持たない。** 毎回ランダムに選ぶので、続けて生成すると語が重なる
  （2回の生成の間で平均、100語で約16語・1000語で約1.6語）。問題になったら「周ごとに読む順番を変える」方式
  （`(a × k + b) mod N`。1周で全語を1回ずつ、書き込みは1ラウンド1行）に移る
- 語彙が空なら AI を呼ばずに終わる。語彙を保存するようになる前に作られた最適化には、最初の生成で共通リストから
  作って保存する（`loadConstraintVocabulary`）。**このときも作成時と同じ下限（100語）を見る。** 届かなければ保存せず、
  AI を呼ばずに終わる（再生成は `GENERATION_FAILED`、補充は `'difficult'`）

### 1文に渡す語の数（2。実測で決めた）

`CONSTRAINT_WORDS_PER_SENTENCE`（`apps/backend/src/generation/prompt.ts`）。**2にする**（下の実測、2026-10-24）。

| 案 | 渡し方 | ねらい |
|---|---|---|
| 2 | 2語の組を渡し、両方を使わせる | 1文に指定の音を含む語が2つ入る |
| 3 | 3語を渡し、自然に使える2語以上を選ばせる | ランダムな組では「雑穀」と「座席」のような意味のつながらない2語が組になる。選ぶ余地を残して文を自然にする。渡す語は1.5倍 |

比べるときは `bun run compare:constraint`（`apps/backend/scripts/compare-constraint-prompts.ts`）を使う。本番と同じ
`generateBatch` を通し、AI だけを wrangler の `getPlatformProxy()` 経由のリモートの Workers AI に（`wrangler login`
の認証を使う。AI Gateway は通さない）、読みだけをローカルの辞書に差し替える。採用率・2回以上含む割合・文頭の割合・
渡した語が現れた割合を集計し、全文を書き出す。**文の自然さは全文を読んで比べる。**

#### 実測（2026-10-24）

`@cf/qwen/qwen3-30b-a3b-fp8`、「ざ」「き」「で」×各案3回（`--chars=ざ,き,で --runs=3`、約230ニューロン）。
「形が崩れた」は、組を無視して1語ごとに1文を書くなど、組と文の対応が失われた AI 呼び出しの数で、全文を読んで数えた
（スクリプトの同名の項目は出力の行数で見るだけなので下限になる）。

| 文字・案 | 採用／出力行 | 10問に届いた | 形が崩れた | 2回以上含む | 文頭 |
|---|---|---|---|---|---|
| ざ・2語 | 65/80（81%） | 3/3 | 0/4 | 94% | 31% |
| ざ・3語 | 50/60（83%） | 3/3 | 1/3 | 66% | 26% |
| き・2語 | 47/60（78%） | 3/3 | 0/3 | 100% | 38% |
| き・3語 | 92/97（95%） | 3/3 | 1/3 | 60% | 41% |
| で・2語 | 45/60（75%） | 3/3 | 1/3 | 73% | 42% |
| で・3語 | 98/120（82%） | 3/3 | 2/4 | 40% | 40% |

- **3語の案は、選ぶ余地を「1語ずつ別の文にしてよい」と読まれる。** 10呼び出し中4回、組を無視して1語ごとに1文を
  書いた（「電球が切れたので交換した」「デスが訪れた」）。指定の音を含む語が1文に1つしか入らず、2回以上含む
  割合が40〜66%に落ちる。崩れなかった回も3語を詰め込んだ文が多い（「下山が斬首を早産した」「正規本気今期は勝つ」）
- **2語の案は形をほぼ保つ**（崩れたのは「で」の1回だけで、1語目の定義文を書いた）。採用率はどちらの案も8割前後で、
  1回の生成で10問に届かなかった回は無い。文頭に指定の音が来る割合は、どちらも3〜4割（以前は全件）
- **2語の案でも、意味のつながらない文が半分ほど残る**（「講座はざるで水を切る」「座席の予約は座薬で決まった」）。
  自然な文もある（「雑事が多いと挫折しやすい」「帰省した貴重な思い出を語った」）。不自然な文の多くは語彙の側に
  原因がある。固有名詞・意味の取りにくい語（「アルディージャ」「ザキ」「財経」）を主語に置いて逃げたり、
  お題に向かない語（「座薬」「ボンデージ」）が組に入ったりしている。この実測の後に、こうした語を共通リストから
  外した（上の「最適化練習の語彙」）

## ごちゃまぜ

**テーマも最適化する音も選ばずに「とりあえず打ちたい」人のための入口。** 生成は最適化練習と同じ流れで、
違うのは**語彙の出どころ**と**検証で指定の連接を見ないこと**だけ。

- 語彙は**共通語彙リストの上から `MIX_VOCABULARY_SIZE`（5000）語**（`mixVocabulary()`。
  `apps/backend/src/generation/vocabulary.ts`）。よく使われる順に並んでいるので、上から取ると知らない語の組を避けられる。
  下のほうは zipf 2.0 前後の珍しい語で、ランダムな2語の組に入ると意味のつながらない文になりやすい
  （最適化の実測で、不自然な文の多くは語彙の側に原因があった）
- 生成のたびに語彙を**シャッフル**し、**2語ずつ組にして**（`CONSTRAINT_WORDS_PER_SENTENCE`）20組を渡す。
  指示は最適化と同じ `constraintRules()`。ラウンドの扱い・件数・書き出しの制限・NG 語・打鍵数の検査も同じ
- 検証で `includesConstraint` を見ない（指定の連接が無いため）。`constraint` の却下数は常に0、`twice` は記録しない
- **語彙を D1 に保存しない**（`constraint_vocabularies` を使わない）。連接で選び直す必要が無く、5000語の JSON を
  1行に持つ意味も無い。分解は Worker の生存中1回だけ
- **短文だけ。** 単語・長文の指示はテーマ名に沿わせるもので、ごちゃまぜには当たらない。
  `POST /prompts/regenerate` は `kind: 'mix'` に `sentence` 以外の形式が来たら `VALIDATION_ERROR` で弾く
- **行は1つだけ**（`themes` の `kind: 'mix'`、名前は `MIX_NAME`＝「ごちゃまぜ」）。利用者が作る操作は無く、
  `GET /themes?kind=mix` で初めて引かれたときに**お題0件で作る**（`findOrCreateMixTheme`）。お題はプレイ画面の
  「作る」（同期再生成）と補充で積む。`POST /themes` を通さないのは、ベータ版で新規作成を弾いている利用者
  （`docs/04-api.md`）が最初の10問を作れなくなるため
  - **不変条件5（テーマ行はお題と同じバッチで挿入）の理由には当たらない。** あの条件が防いでいるのは
    「公開一覧にお題ゼロのテーマが残る」ことで、ごちゃまぜは公開一覧（`kind` で絞る）に出ない
- 補充・クォータの扱いはテーマ・最適化と同じ（ログインユーザーのプレイでだけ補充が走り、使ったニューロンを
  そのユーザーに加算する。匿名ユーザーは在庫を遊ぶだけ）

## リトライの規則

**最大2ラウンド（初回＋リトライ1回）。各ラウンドとも常にフル件数（単語40・短文20・長文5）をリクエストする。**

| パス | 目標 | 未達時 |
|---|---|---|
| 新規テーマ作成（同期） | 有効10件（**短文のみ**） | `GENERATION_FAILED` を返しテーマ名の変更を促す。**テーマ行は作らない** |
| 同期再生成（短文） | 有効10件 | `GENERATION_FAILED`。**1件も保存しない** |
| 同期再生成（**単語・長文**） | 有効20件／1本 | **取れた分を保存する。** 1件も作れなかったときだけ失敗（`docs/04-api.md`） |
| バックグラウンド補充（非同期） | その形式の在庫 ≥ オフセット + 目標 | `'difficult'` を立てる。**単語・長文は「1件も作れなかった」ときだけ** |

**単語と長文で条件を分けているのは、目標と上限が近いため**（`acceptsPartialBatch()`）。
1回の生成で作れるのは単語で最大80件、長文で最大10本しかなく、重複や却下でここから減る。
短文と同じ扱いにすると、少し届かないだけで有効なお題とニューロンを捨て、普通に作れている
テーマにまで「生成困難」の印が付いて補充が止まる。

### 単語の1プレイを20問にしている理由

1プレイの打鍵量を短文（約220打）に近づけるため。20問で約160打になる。

**Yahoo API 時代も20問だった。** 読み取得が1語につき外部サブリクエストを1回使い
（上限1実行50回）、30問だと採用率75%を要求されて届かなかった。読み Worker
（Vibrato + UniDic トリム辞書）への差し替えで読み取得は1ラウンド1回のバッチ呼び出しに
なったため一度30問に上げたが、1プレイを軽くする方針で20問に戻した。
値は `packages/shared/src/session.ts` の `PLAY_SIZE_WORD` 1か所。

### この2ラウンド制限は勝手に変えてはいけない

読み取得は1ラウンドにつき読み Worker への Service Binding を1回呼ぶ（バッチ形）。
その1回が受け付けるのは **`MAX_TEXTS`（40件）まで**なので、各形式の1ラウンドの依頼数は
それを超えないこと。**読み取得に渡すのも依頼した件数まで**（最適化で、20組に60行を返した実測がある。
切らないと上限を超えて読み取得が断られ、ニューロンを使ったあとに生成ごと落ちる）。数えるのは生の出力行ではなく、
無料の検査（重複・文字種・NG 語・漢字・書き出し）を通った分。先に切ると、前置きの1行が枠を使って最後の正しい文が落ちる。
残る外部呼び出しはラウンドごとの Workers AI の
1回だけで、サブリクエスト上限（50回）には十分な余裕がある。

ラウンド数を増やすと増えるのは Workers AI の呼び出し回数とレイテンシーなので、
変更は採用率の実測を見てからにすること。

## バッチ間の重複対策

呼び出しはステートレスなので、2回目のバッチは1回目が何を作ったか知らない。対策は**2段**ある。

| 段 | 場所 | 効く範囲 | 状態 |
|---|---|---|---|
| 完全一致の除去 | `batch.ts` の `seen`（`new Set(input.existing)`） | 既存お題と**同一の文** | **有効** |
| プロンプトへの文脈 | `prompt.ts` の `INCLUDE_EXISTING_PROMPTS` | 言い回しの近い**別の文** | **いまは外している（試行中）** |

`seen` は読み取得の前に無料で弾く（既存お題の本文は `EXISTING_CONTEXT_SIZE` = 直近30件、**単語は200件**を取ってくる）。この段が生きている限り、**同じ文が二度プールに入ることはない。**

**弾いた数は `dup` として計測する。** 以前はカウンタを通さずに捨てていたため、**AI Gateway 上は「ほとんど却下されていない健全な生成」に見えるのに、実際の採用はごくわずか**という食い違いが起きた（福岡の単語プールで実際に起きた）。重複は却下の中で最も増えやすい要因なので、内訳に出しておく。

### プロンプトへの文脈を外して試している（2026-09-06〜）

直近30件を「これと似た内容・似た言い回しは避けろ」という否定の文脈として渡していたが、**モデルが内容ではなく形式の方に引きずられている疑いがある。** few-shot と同じで、否定で添えても例示は例示として効くため、お題の型（文の長さ・構文・主語の立て方）が既存に揃っていく。

**「慣れが生じない」ことがこのサービスの目的なので、型が揃うのは重複そのものより悪い。** 同じ文が出ないことは `seen` が保証しているため、外して失うのは「言い回しの近い別の文」の抑制だけ。

戻すときは `INCLUDE_EXISTING_PROMPTS` を `true` にする。載せる場合の入力トークンの増加は1バッチあたり約4ニューロン（0.005円程度）で、コストは判断材料にならない。**判断は却下率・重複率の実測（Phase 8）で行う。**

## 生成物の検証（お題の質）

打鍵できるかどうか（文字種・打鍵数・指定文字）とは別に、**お題としての質**をここで担保する。

| 検査 | 却下コード | 段階 | 理由 |
|---|---|---|---|
| 漢字を1つ以上含む | `kanji` | 読み取得の前（無料） | ひらがなだけの文は打てるが、画面に出るのは表記の方で、漢字かな混じり文を読みながら打つ練習から外れる |
| 同じ書き出しが上限まで無い | `opening` | 同上 | 1回の生成が1つの型で埋まるのを止める |
| NG 語を含まない | `ng` | 同上 | 卑猥な語・差別語などをお題に出さない。**最適化・テーマの全形式で見る** |

### NG 語の検査

リストは `packages/shared/src/generation/ng-words.ts`（`NG_WORDS`）。
[MosasoM/inappropriate-words-ja](https://github.com/MosasoM/inappropriate-words-ja)（MIT）の
`Sexual.txt`・`Offensive.txt` のうち打てる文字だけの語と、最適化の共通語彙リストを目で確かめて足した語からなる。
判断が分かれる語（痴漢・盲目・ゲイ・裸 など）も外す側に倒している。

**照合は語の種類で分ける**（`containsNgWord`）。

| NG 語 | 照合 | 理由 |
|---|---|---|
| 1文字（盲・裸・糞・姦） | **見ない** | 部分一致だと「盲点」「裸足」まで落とす |
| カタカナだけ | カタカナの連なり全体と一致したときだけ | 部分一致だと「イク」が「バイク」「マイク」、「カス」が「カステラ」、「エロ」が「ピエロ」に当たる。共通語彙リストだけで88語が巻き込まれた（実測） |
| それ以外（漢字を含む・ひらがな） | 本文への部分一致 | 「〜だ」「〜が」と助詞が続く書き方を拾うため緩めない。巻き込みは「ちびっこ」「ぱちんこ」くらい |


### 同じ書き出しの制限

先頭4文字が同じお題は、**1回の生成につき3本まで**（`OPENING_PREFIX_LENGTH` / `OPENING_MAX`）。

**プロンプトが効かなかったときの歯止め。** 「し」を指定すると、モデルは「しんしんと」を見つけて21件中14件をそれで埋めてきた（実測）。完全一致ではないので `seen` は素通りし、そのままプールに入ると「毎回違うお題」という前提が崩れる。

- 4文字なのは、「しんしんと」を削りつつ「しんぶん」「しんこう」「しんぱい」を別物として残せる粒度だから
- **既存お題は数えない。** 止めたいのは1回の生成の中の偏りで、過去のプールに何本あるかは別の話。既存を数えると、偏った状態で作られたプール（実測で同じ書き出しが23本）に塞がれて補充が失敗する
- ラウンドはまたいで数える（2ラウンド目で同じ型を作り直させない）

### 「含む」モードの偏り（2026-09-06の実測。語を渡す方式にする前の記録）

指示を足すたびに**別の抜け道に逃げる**ので、1つずつ塞いだ経過を残す。

| 指示 | 結果 |
|---|---|
| 「語頭に来る文は○個まで」 | **効かない。** 全体を数えさせる指示は守られない（文頭21/21） |
| 「どの文も指定文字を含まない語から書き始める」 | 文頭0%になるが、**文末の接続助詞に逃げた**（「〜したし」「面白し」。日本語として壊れる） |
| ＋「助詞や語尾として付け足さない」 | 日本語は自然になるが、**文頭に戻る**（「し」では100%） |

**位置の偏りは文字によって難易度が違う。** 「し」「ぴ」は語彙のほとんどが語頭に来るため、文中に置くこと自体が無理筋になる。「ざ」では文頭74%→56%まで下がった。

**擬音語・擬態語は勧めない側に倒さない。** 一度「使うと入れやすい」と書いたら「しんしんと」を量産したが、量産は `opening` の検査で止まるようになったため、語彙を狭める必要がなくなった。「ぴ」のように擬音語が語彙の中心にある文字では、禁じると生成そのものが失敗する。

### 却下率の実測（2026-09-06、qwen3 + `/no_think`。語を渡す方式にする前の記録）

| 文字 | 有効 | charset | kanji | opening | keystroke | constraint |
|---|---|---|---|---|---|---|
| ぴ（新規作成） | 17 | 0 | 11 | 少 | 0 | 0 |
| ぬ（新規作成・失敗） | 11 | 0 | 0 | 2 | 0 | **27** |
| ざ（補充） | 18 | 0 | 少 | 少 | 0 | 12 |

**`constraint` が最大の却下要因**。モデルが指定文字を読みに入れられないケースで、プロンプトでも検証でも減らせない。「ぬ」はこれで目標に届かず、新規作成が失敗する。プリセットに置く文字は、実際に作れるかを確認してから決めること。

## 読み仮名の取得

**必ず `getReadings()` の抽象化を経由する。読み Worker を直接呼ばない。**

```ts
getReadings(texts: string[]): Promise<ReadingOutcome[]>
```

実装は読み Worker（`apps/reading`。Vibrato + UniDic cwj-3.1.1 トリム辞書、Service Binding 経由・外部非公開）。1回の呼び出しで最大40件（`MAX_TEXTS`）まで。
辞書に読みが無い語は `UNKNOWN_READING` として返り、呼び出し側はそのお題を却下する。

Yahoo! JLP API は個人での商用利用が不可だったため撤去済み（#177）。

読みはお題生成時に一度だけ計算してD1に保存する。プレイのたびに呼ぶのではない。

**返す読みは必ずひらがなに揃えること。** 読み Worker はカタカナの読み列を返すので、ローマ字候補テーブルに渡す前にカタカナ→ひらがな変換を通す（`katakanaToHiragana`）。

テーブルに無いかなが読みに残っていた場合は `UnsupportedKanaError` を投げ、呼び出し側がそのお題を却下する。

## 生成の発火条件（バックグラウンド補充）

プレイ開始でオフセットを更新した後に判定する。

**判定も補充も、遊んでいる形式のプールに対して行う**（短文を遊んでも単語は補充しない）。

```
残り = その形式の在庫 − 更新後オフセット

残り ≥ 在庫目標 → 何もしない
残り < 在庫目標 → ログインユーザーかつ allowRefill フラグ（Next.jsが
                 残ニューロンを判定した結果）が true なら補充をキック
                 匿名ユーザーや残数0ならキックしない
```

- 在庫目標は**形式ごと**（短文20・単語40・長文3本。`docs/03-data-model.md`）。
  目標は「件数」ではなく**在庫水準**（その形式の在庫 ≥ オフセット + 在庫目標）
- 残ニューロンの判定はNext.js側が行い、`allowRefill` フラグとしてHonoへ渡る（`docs/04-api.md` の「判定と記録の分担」）
- `theme:<theme_id>:<form>:lock` で多重起動を防ぐ。最初の1件だけがロックを取得し、他はスキップする。**キーは形式ごと**（単語の補充中に短文の補充を止めない）
- `ctx.waitUntil()` を使い、レスポンスは待たせない
- **AIを呼んだ分は、成否によらず加算する。** お題が1件も増えなくても、読み取得の例外で落ちても、ニューロンは消費されている（`docs/04-api.md`）

## モデルの切り替え

`MODELS`（`apps/backend/src/generation/model.ts`）に登録したモデルを、`GENERATION_MODEL`（`wrangler.jsonc` の vars）で切り替える。**既定は `@cf/qwen/qwen3-30b-a3b-fp8`**（登録に無い値は既定にフォールバック）。品質・速度・コストの実測（Phase 8）で確定済み。

比較候補と実測値（テーマ「忍者」8件・2026-09-05）。**モデルIDは推測で書かず `wrangler ai models` で確認すること**（存在しないIDを渡すと実行時に `5007: No such model` で落ちる）。

| モデル | 時間 | 採用 | ニューロン | 備考 |
|---|---|---|---|---|
| `@cf/qwen/qwen3-30b-a3b-fp8` + `/no_think` | 0.9〜1.6秒 | 6〜7/8 | 3.7〜4.2 | **既定** |
| `@cf/zai-org/glm-4.7-flash` | 24〜132秒 | 8/8 | 96〜215 | 品質は最高だが同期生成には遅すぎる |
| `@cf/meta/llama-3.1-8b-instruct-fp8` | 2〜8秒 | 0〜8/8 | 4〜6 | 書式を崩すことがある |

**Qwen3系には `/no_think` を付ける。** 推論モデルの「思考」も課金対象の出力トークンで、生成は1トークンずつ進むため時間にも直結する。お題生成は探索を要する問題ではないので思考させても品質は上がらず、むしろ思考中の連想メモに引きずられて内容が劣化する（実測で「忍者」の連想に `電話` `電車` `会社` が混ざり、それが最終出力に現れた）。

モデル固有の指示は `MODELS` の設定として持ち、パイプラインの中で分岐させない。

### 消費ニューロンの計算

**応答にニューロン数は入っていない。** `env.AI.run` が返す `usage` はトークン数だけ（`prompt_tokens` / `completion_tokens`）で、`usage.neurons` は存在しない。**日次上限の判定に使う値なので、モデル別の単価を掛けて自分で出す**（`MODELS` の `neurons`、計算は `neuronsUsed()`）。

| モデル | 入力（/百万トークン） | 出力（/百万トークン） |
|---|---|---|
| `@cf/qwen/qwen3-30b-a3b-fp8` | 4,625 | 30,475 |
| `@cf/zai-org/glm-4.7-flash` | 5,500 | 36,400 |
| `@cf/meta/llama-3.1-8b-instruct-fp8` | 13,778 | 26,128 |

既定モデルでの実測は**1ラウンド（30件リクエスト）で約6.5ニューロン**（20件時点の計測値）（2026-09-08、ローカルで新規作成1回）。出典は [Workers AI Pricing](https://developers.cloudflare.com/workers-ai/platform/pricing/)。**料金が変わったら `MODELS` を直す。** Cloudflareはモデル別の単価表示に変えたが、課金の裏側は引き続きニューロン。

単価かトークン数のどちらかが取れなければ**0**として扱う。推定値で埋めると、消費していない分まで利用者の枠を削ることになる。

### 枠を使い切ったときのエラー

無料枠（アカウント全体で1日10,000ニューロン）を超えると、Workers AI は **3036**（429）を返す。**Freeプランには超過課金の経路が無く、請求は発生せずエラーになるだけ**で、枠は 00:00 UTC に戻る。似た429に **3040**（Out of Capacity）があり、こちらは数分で直りうる。

`classifyAiError()`（`generation/ai.ts`）でこの2つを判別し、`AI_QUOTA_EXCEEDED` / `AI_UNAVAILABLE` として返す（`docs/04-api.md`）。**`GENERATION_FAILED` に落とさない。** 「テーマ名を変えて」は、名前を変えても直らない原因に対する誤誘導になる。

**背景補充では何もしない。** 誰も待っていない処理なので伝える先が無く、ログに残すだけ。利用者は在庫が尽きた時点で「作り足す」を押し、そこで同期生成のエラーとして正しい理由を受け取る。**このとき `generation_status = 'difficult'` を立てないこと。** アカウント側の枠切れは「このテーマは生成しにくい」とは別物で、印を立てると枠が戻った後も補充が止まる。

記録は `batch.ts` の **`onNeurons` でラウンドごとに、AIの応答が返った直後**に行う（完了を待ってから次へ進む）。戻り値（`BatchResult.neurons`）を待ってまとめて書くと、読み仮名の取得で例外が飛ぶ経路と、**クライアント切断でinvocationごと打ち切られる経路**で「AIは消費したのに記録されない」状態になる。`BatchResult.neurons` は合計値で、応答に載せる `neuronsUsed` に使う。

**`max_tokens` を明示すること。** モデル側の既定は2000で、推論モデルは思考だけで使い切って本文が空のまま返る。

**応答の形はモデルによって違う。** Workers AI の従来形 `{ response }` と OpenAI互換形 `{ choices[0].message.content }` の両方があるため、テキストの取り出しは正規化して受ける。これはモデルごとの分岐ではないので「モデル名で分岐しない」方針とは矛盾しない。

呼び出しは**AI Gateway経由**にする。

```ts
await env.AI.run(model, input, {
  gateway: {
    id: "henge",
    skipCache: true,
    metadata: { themeId, kind, round, path },
  },
})
```

これでレイテンシ・コスト・回数がダッシュボードに記録され、比較用の計測コードを自前で書かずに済む。生成したお題には `prompts.model` にモデル名を残し、どのモデルが作ったお題か後から辿れるようにする。

**`skipCache: true` を必ず付ける。** AI Gatewayのキャッシュが効くと、同じテーマに同じお題が返る。「毎回違うお題」というHENGEの前提が壊れるため、ダッシュボード側の設定に依存させない。

ゲートウェイは Authenticated Gateway を有効にする。バインディング経由の呼び出しは事前認証済みのため、APIトークンは発行しなくてよい。

## 計測

**呼び出しには必ずカスタムメタデータを付ける。** AI Gatewayのログは「AIとのやりとり」しか知らないため、これが無いと「どのテーマの生成か」でログを絞り込めない。

メタデータは**1リクエストにつき5件まで**（超過分は黙って捨てられる）。**出題の形式のためにキーを増やせない**ので、`path` の値に畳んである（`regenerate:word` / `refill:word`）。短文の値は変えていないため、既存の絞り込みはそのまま使える。値は文字列・数値・真偽値のみで、オブジェクトは入らない。枠の割り当ては次のとおり。

| キー | 付けるタイミング | 値 |
|---|---|---|
| `themeId` | リクエスト時 | テーマID |
| `kind` | リクエスト時 | `theme` / `constraint` |
| `round` | リクエスト時 | `1` / `2` |
| `path` | リクエスト時 | `create` / `regenerate` / `refill`（**単語は `regenerate:word` / `refill:word`**） |
| `counts` | `patchLog()` | `"charset:3,kanji:1,opening:2,keystroke:4,constraint:1,punct:0,ng:0,dup:2,twice:5"` |

### 検証結果をログに書き戻す

生成の成否は、AIが応答した時点では分からない。読み取得と検証を通した後に判明する。この時間差は `patchLog()` で埋める。

```ts
const res = await env.AI.run(model, input, { gateway: { /* 上記 */ } })
const logId = env.AI.aiGatewayLogId

// ... ホワイトリスト検査 → getReading() → 打鍵数検査 → 「含む」検査 ...

ctx.waitUntil(
  env.AI.gateway("henge").patchLog(logId, {
    score: Math.round((valid / N_request) * 100),
    // **枠は残り1件しかない。** 内訳は必ず1つの文字列に畳む（下記）
    metadata: { counts: `charset:${c},kanji:${j},opening:${o},keystroke:${k},constraint:${n}` },
  }),
)
```

**却下率はここで見る。D1に却下数を記録するテーブルを作らない。** Phase 8のモデル比較と同じダッシュボードに並ぶ。

却下されたお題はD1に保存されないため、`prompts` テーブルからは却下率を計算できない（分母が残らない）。一方でAI Gatewayのログには落選分を含む生の応答が残っているので、原因を追うときはログ本文を読む。

**内訳は1つのキー（`counts`）に畳んで入れる。** メタデータは1リクエストにつき5件までで、リクエスト時に4件使っているため**patchLog で使える枠は残り1件だけ**。ここでキーを分けると6件目が黙って捨てられ、却下の内訳か採用の計測のどちらかが消える。例外もログも出ないので、ダッシュボードを開くまで気付けない。**項目を増やすときはこの文字列に足す。**

| ラベル | 意味 |
|---|---|
| `charset` | 却下。ホワイトリスト検査。打てない記号などが混ざっていた |
| `kanji` | 却下。漢字が1つも無い（ひらがなだけの文） |
| `opening` | 却下。同じ書き出しの文が既に採用上限まである |
| `keystroke` | 却下。打鍵数が10〜35の範囲外 |
| `constraint` | 却下。「含む」モードで、指定文字が読み仮名に無かった |
| `punct` | 却下。**長文のみ。** 文の終わり（。！？）が足りず、区切りの無い文章だった |
| `ng` | 却下。NG 語（卑猥な語・差別語など）が入っていた |
| `dup` | 却下。既にプールにある（または同じ生成の中で重なった）ため落とした |
| `twice` | **却下ではなく採用側の計測。** 指定文字を2回以上含んだ採用お題の数（最適化モードのみ） |

同じ却下率でも原因が違えば打ち手が変わる（記号ならプロンプトの指示、打鍵数なら長さの指示、含む文字ならテーマ自体の難しさ）。合計ではなく内訳で残すこと。

`patchLog()` は同期生成の待ち時間を増やさないよう `ctx.waitUntil()` に逃がす。

**`patchLog()` が外部サブリクエストを消費するか、Phase 3で実測すること。** バインディング経由なので内部扱いのはずだが、ドキュメントに明記が無い。
